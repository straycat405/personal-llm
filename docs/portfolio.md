# BTLLM — 개인 PC에서 동작하는 로컬 RAG 문서 비서

> 이 문서는 채용 담당자·면접관이 읽는 포트폴리오 본문이다.
> 측정 원본과 작업 과정은 [`portfolio-improvement-log.md`](portfolio-improvement-log.md)에,
> 세션 간 인수인계는 [`../HANDOFF.md`](../HANDOFF.md)에 있다.

## 1. 프로젝트 오버뷰

### 해결하려는 문제

긴 문서를 다 읽지 않고 필요한 답만 얻고 싶지만, 그 문서가 외부로 나가면 안 되는 상황이 있다.
정부 공고문, 계약서, 사내 매뉴얼, 개인 기록이 그렇다. 상용 LLM API는 품질이 좋지만 문서 본문이
외부 서비스로 전송되고 사용량만큼 과금된다.

BTLLM은 **문서가 로컬 밖으로 나가지 않는 RAG 문서 비서**다. 사용자가 PDF·문서·URL을 올리면
로컬에서 임베딩·색인하고, 로컬 LLM이 검색된 근거만으로 답하며 사용한 파일명을 출처로 표시한다.

### 아키텍처

```
[React + TypeScript]
        │  WebSocket (토큰 스트리밍)  /  REST (인증·문서·이력)
        ▼
[Spring Boot 3.5 + Spring AI 1.1]
        │
        ├─ ChatClientFactory ── Advisor 체인(가드 → 대화이력 → 토큰추적 → 로깅)
        │                       provider 라우팅: ollama / openai / claude / gemini
        │
        ├─ LlmTools (Tool Calling)
        │     └─ searchKnowledgeBase ─▶ pgVector 검색 ─▶ HybridReranker 재정렬
        │
        └─ EtlPipelineService (@Async)
              Reader → TokenTextSplitter → 임베딩 → pgVector
        │
        ▼
[Ollama: qwen3:8b (생성) + bge-m3 (임베딩)]   [PostgreSQL + pgvector]
```

### 실행 환경 — 이 프로젝트의 모든 수치가 나온 제약 조건

| 항목 | 값 |
|---|---|
| GPU | RTX 4060 Ti **8GB** |
| VRAM 점유 | qwen3:8b 약 5.6GB + bge-m3 약 0.7GB |
| 여유 | 약 1.7GB — 브라우저 등이 GPU를 쓰면 즉시 포화 |

**이 8GB 제약이 프로젝트의 거의 모든 기술적 의사결정을 규정한다.** 아래 트레이드오프와
트러블슈팅 대부분이 "제한된 VRAM에서 무엇을 포기할 것인가"의 문제다.

## 2. 핵심 성과 지표

모든 수치는 골든셋 기반 자동 평가 하네스의 실측값이다. 재현 명령은 각 항목에 표기했다.

### 2-1. LLM 응답 품질 — 로컬 모델이 상용 API와 동등 수준 도달

동일 골든셋 8문항, 동일 검색 파이프라인, 모델만 교체 (`providerComparisonExperiment`).

**3회 반복 실행**(각 provider 24회 호출) 기준이다.

| Provider / 모델 | 문항 통과율 | 필수 사실 포함률 | 평균 지연 | p95 |
|---|---:|---:|---:|---:|
| **로컬 qwen3:8b** (RTX 4060 Ti 8GB) | 50.0% (12/24) | **77.8% (49/63)** | 88.9s | **188.6s** |
| gpt-4o-mini (상용 API) | **58.3% (14/24)** | **77.8% (49/63)** | 4.9s | 7.1s |

- **근거 활용도는 동일하다.** 필수 사실 포함률이 소수점까지 같은 77.8%다.
- **문항 통과율은 상용이 8.3%p 앞선다.** 통과 조건은 사실 100% 포함 + 금지 오답 0건이므로,
  같은 양의 사실을 뽑고도 로컬이 오답을 더 자주 섞는다는 뜻이다.
- **실사용 격차는 지연에 있다.** 평균 18배, p95는 188.6초 대 7.1초다.

컨텍스트 예산을 고치기 전(8장)에는 로컬이 25.0% / 33.3%였다. 즉 로컬과 상용의 품질 격차로
보였던 것의 **대부분은 모델 체급이 아니라 우리 파이프라인의 결함**이었고, 그것을 걷어내자
근거 활용도는 같아지고 오답률과 속도만 남았다.

### 2-2. RAG 답변 품질 개선 (`ragGenerationQualityExperiment`)

컨텍스트 초과를 해소한 것이 단일 조치로는 가장 큰 개선이었다(8장).

| 조치 | 문항 통과율 | 필수 사실 포함률 | 평균 지연 |
|---|---:|---:|---:|
| 기준선 (청크 1500) | 0.0% (0/8) | 38.1% | 65.8s |
| **청크 800으로 축소** | **50.0% (4/8)** | **76.2%** | **50.6s** |

이 값(76.2%)은 동일 골든셋에서 gpt-4o-mini가 기록한 필수 사실 포함률과 같다.

> 초기 재정렬 실험은 12.5% → 25.0%였으나, 이후 평가 코퍼스가 21청크·31,096자에서
> 38청크·206,147자로 바뀌어 위 표와 직접 비교되지 않는다. 표의 두 값은 동일 코퍼스에서
> 측정한 통제된 비교다.

### 2-3. 청크 크기 트레이드오프 (`ragAccuracyExperiment`, 골든셋 35건)

| 청크 크기 | 청크 수 | 임베딩 소요 | 운영설정 Recall |
|---|---:|---:|---:|
| 800 | 66 | 31,418ms | 100% |
| **1500 (채택)** | 35 | 6,555ms | 88.6% |
| 3000 | 19 | 2,483ms | 82.9% |

### 2-4. 콜드스타트 제거

| 조건 | 응답시간 |
|---|---:|
| 모델 언로드 상태 | 37,197ms |
| `keep-alive: -1s` 적용 후 | 1,246ms |

**약 30배 개선.**

### 2-5. 부하 특성 (k6, `chat-stream-test.js`)

| 조건 | 결과 |
|---|---|
| VRAM 포화 (7.78GB/8GB) | 토큰 생성 0.86 t/s, 33건 중 **0건** 완료 |
| VRAM 확보 (6.55GB) | 33건 중 4건 완료, TTFT avg 13.9s / p95 25.0s |
| WebSocket 연결 자체 | avg 2.6ms |

## 3. 주요 기술적 의사결정과 트레이드오프

### 3-1. 상시 RAG Advisor → Tool Calling 전환

**결정**: 모든 메시지에 벡터 검색을 붙이던 `QuestionAnswerAdvisor`를 제거하고,
모델이 필요할 때 호출하는 `searchKnowledgeBase` Tool로 바꿨다.

**트레이드오프**: 잡담에 불필요한 임베딩 호출과 컨텍스트 오염이 사라지는 대신,
**"검색이 실행되는가"의 결정권을 모델에게 넘긴다.** 작은 로컬 모델에서는 이 위임이
실제로 위험했고, 그 대가를 트러블슈팅 4-2에서 치렀다.

### 3-2. 청크 1500 토큰 — 정확도를 주고 속도를 샀다

**결정**: 기본값 800 대신 1500 채택.

**근거와 대가**: 임베딩 소요가 31.4초 → 6.6초로 약 5배 줄지만, 운영 설정 기준 Recall이
100% → 88.6%로 **11.4%p 하락**한다. 데모·개인 사용 규모에서는 색인 대기 시간이 체감상 더 크다고
판단해 정확도를 일부 포기했다. README에 있던 "임베딩 호출 50% 감소"라는 서술에 **정확도 손실이
빠져 있던 것을 실측으로 드러내고 문서를 교정**했다.

### 3-3. cross-encoder 리랭커를 쓰지 않고 직접 계산 재정렬

**상황**: 벡터 유사도만으로는 부록·목록 청크가 정답 청크를 밀어내고 있었다. 업계 표준 해법은
cross-encoder 리랭커(`bge-reranker-v2-m3`)다.

**결정**: 쓰지 않았다. Ollama에 `/api/rerank`가 없어 별도 `llama.cpp` 서버가 필요하고,
이미 6.3GB를 쓰는 8GB VRAM에 세 번째 모델을 상주시키면 **앞서 실측한 VRAM 포화 시 0.86 t/s
붕괴**를 재현할 위험이 컸다.

**대안**: 후보 풀을 3 → 10으로 넓게 가져와 **벡터 점수 0.7 + 질의 키워드 겹침 0.3** 가중합으로
순수 Java 재정렬 후 상위 3개만 프롬프트에 전달. 새 프로세스도, 추가 VRAM도 없다.

**결과와 한계**: 통과율 12.5% → 25.0%. 다만 재정렬은 **이미 검색된 후보의 순서만 바꾸므로**
정답이 애초에 후보에 없는 Recall 실패에는 무력하다는 것을 함께 확인했다(→ 5장).

### 3-4. 상용 API를 대체재가 아니라 '측정 기준선'으로 도입

**문제**: 로컬 모델만 측정하면 실패할 때마다 *검색이 근거를 못 준 것*인지 *모델이 근거를 받고도
못 쓴 것*인지 구분할 수 없다. 이 구분 없이는 다음 개선을 검색에 투자할지 모델에 투자할지
결정할 근거가 없다.

**결정**: 동일 골든셋·동일 검색 파이프라인·동일 시스템 프롬프트에 **모델만 교체**하는
비교 실험을 만들었다. 상용 모델은 제품의 대체재가 아니라 **실패 원인 분해용 기준선**이다.

**성과 — 실패가 세 갈래로 분해됐다** *(아래 표는 청크 1500 시점의 값이다. 컨텍스트 초과를
고친 뒤 결과가 크게 달라졌으므로 최신 수치는 9장을 볼 것. 이 절은 당시의 판단 근거를
보존하기 위해 남긴다)*:

| 문항 | 로컬 | GPT | 해석 |
|---|---:|---:|---|
| `prize-1`, `registration-1` | ❌ | ❌ | **검색 문제** — 근거 자체가 후보에 없음 |
| `track-1`, `round-general-1`, `application-1` | ❌ | ✅ | **모델 체급 문제** — 같은 근거로 GPT는 성공 |
| `eligibility-1`, `round-local-1` | ✅ | ✅ | 정상 — 회귀 감시용 |

특히 `application-1`은 로컬 0/4, GPT 4/4였다. 검색 결과가 동일했으므로 이 실패는 검색이 아니라
소형 모델의 추출 능력 문제로 확정된다 — **고 당시에는 판단했다.**

> **이 판단은 나중에 틀린 것으로 밝혀진다.** 두 모델이 *동일하게 잘린 근거*를 받고 있다는
> 공통 조건을 비교로는 볼 수 없었기 때문이다. 컨텍스트를 고치자 `application-1`은 로컬에서도
> 4/4가 됐다(8장). **비교 실험은 두 조건에 공통으로 걸린 결함을 드러내지 못한다**는 것이
> 이 프로젝트에서 얻은 가장 값비싼 교훈이다.

## 4. 트러블슈팅

각 항목은 `발견 → 진단 → 개선 → 검증` 네 단계에 수치를 갖는다.

### 4-1. 성능 개선 설정 한 줄이 채팅 전체를 마비시킨 회귀

- **발견**: 콜드스타트 제거를 위해 `keep-alive`를 적용한 직후 k6 baseline **에러율 100%**.
- **진단**: 로컬 프록시(`http.server`)로 백엔드→Ollama 요청을 가로채 원문 확보 →
  응답 본문이 `{"error":"time: missing unit in duration \"-1\""}`.
  YAML에 정수 `-1`로 썼으나 Spring AI의 `keepAlive` 필드가 String이라 `"-1"`로 직렬화되고,
  Ollama의 Go `time.ParseDuration`이 단위 없는 값을 거부(400)하고 있었다.
- **개선**: `-1s`로 단위 명시.
- **검증**: 200 OK, `ollama ps`에서 `UNTIL: Forever`, 에러율 **100% → 0%**,
  콜드스타트 **37,197ms → 1,246ms**.
- **교훈**: Spring Boot의 relaxed binding이 숫자를 조용히 문자열로 바꾼다.
  **기동 성공 ≠ 동작 정상** — 설정값의 *형식*까지 실제 요청 로그로 검증해야 한다.

### 4-2. Advisor→Tool 전환 후 RAG가 완전히 죽어 있던 문제

- **발견**: PDF 색인 후 "방금 준 문서 무슨 문서야?" → "어떤 문서도 제공받지 않았어요".
- **진단 ①**: `vector_store` 직접 조회 → 21청크 정상 적재. ETL 문제 아님.
- **진단 ②**: 도구 호출 로그 **0건**. Ollama API를 직접 격리 테스트하니
  기존 description(`"…필요할 때만 사용하세요"`)은 `tool_calls: null`,
  단정형으로 바꾸면 정상 호출 → **원인은 description의 어조**였다.
- **개선**: description을 억제형에서 단정형으로, 시스템 프롬프트에 도구 존재와 호출 조건 명시,
  도구 호출 로그 추가(원인 추적이 로그 부재로 어려웠던 점을 반영).
- **추가 발견**: 도구는 호출되나 **적중 0건**인 케이스 — "무슨 문서야?" 같은 *메타 질문*은
  문서 *내용*과 의미적으로 유사하지 않아 벡터 검색이 구조적으로 0건을 낸다.
  0건일 때 문서 목록을 대신 반환하도록 보완했다.
- **검증**: 호출률 **0% → 100%**.
- **교훈**: 상시 Advisor를 Tool로 바꾸는 것은 성능 최적화처럼 보이지만 실제로는
  **동작 여부의 결정권을 모델에게 넘기는 설계 변경**이다. 작은 로컬 모델은 description 어조
  하나로 호출률이 0%와 100%를 오간다.

### 4-3. 실시간 답변에서만 Markdown 개행이 사라지던 문제

- **발견**: 스트리밍 중에는 제목·목록·표가 한 줄로 붙는데, **새로고침하면 정상** 렌더링.
- **진단**: 같은 원문에 대해 실시간 화면과 저장본이 다르다는 점에서 CSS가 아니라
  **전송 경로와 저장 경로의 불일치**로 좁혔다. `TokenTrackingAdvisor`는 모든 청크를 저장하는데
  WebSocket 핸들러는 `text.isBlank()`인 청크를 버리고 있었고, Ollama는 Markdown 줄바꿈을
  독립적인 공백 청크로 전송하고 있었다.
- **개선**: 필터를 `isEmpty()`로 좁혀 내용 없는 청크만 제외하고 줄바꿈은 보존.
- **검증**: 실제 qwen3:8b 요청에서 제목·목록·표·코드 블록이 스트리밍 화면에서 정상 분리,
  새로고침 후 동일 구조 유지.
- **교훈**: 같은 데이터의 두 경로를 비교하는 것이 원인 격리의 결정적 단서였다.

### 4-4. 프롬프트만으로는 지시 준수에 한계가 있음을 실측으로 확인

- **발견**: 대화 품질 기준선에서 자동 통과율 **0%**. 그러나 상세 응답을 보니 기억·주제 전환·
  Markdown 계약은 모두 충족하고 있었고, **문서 검색을 하지 않은 모든 일반 답변에 `[출처]`가
  붙는 것**과 서비스 이름을 모르는 것이 공통 원인이었다.
- **진단**: 모델 이해력 실패가 아니라 **시스템 프롬프트의 정책 오류**였다.
  "사용한 문서 파일명을 출처로 표시" 규칙이 비-RAG 답변까지 일반화되고 있었다.
- **개선 1차**: 서비스 정체성 명시 + 출처 규칙을 조건부로 수정 → 통과율 0% → **41.7%**.
- **개선 2차**: few-shot 예시와 자기 점검 지시 추가 → 정체성 **0/3 → 3/3**.
- **남은 한계(정직하게)**: `context-shift-1`에서는 여전히 3/3으로 `[출처]`가 붙는다.
  이 시나리오는 이전 턴에 *문서와 흡사한 배경 지식*을 심어주는데, 모델이 실제 도구 호출 여부와
  무관하게 "문서 얘기니까 출처를 붙인다"고 패턴 매칭한다.
- **교훈**: 프롬프트 지시 + few-shot으로 끌어올릴 수 있는 지시 준수에는 상한이 있다.
  확실한 보장이 필요하면 **결정론적 가드레일(코드 레벨 후처리)**을 병행해야 한다.
  현재는 영향도를 고려해 백로그로 관리 중이다.

### 4-5. OpenAI provider 추가 중 겪은 Spring AI 구성 함정 3종

- **발견 ①**: 스타터를 추가하자마자
  `expected single matching bean but found 2: ollamaEmbeddingModel, openAiEmbeddingModel`로 기동 실패.
- **진단 ①**: 양쪽 임베딩 오토컨피그를 디컴파일해 확인하니 둘 다
  `@ConditionalOnProperty(matchIfMissing=true)` — **속성을 명시하지 않으면 둘 다 활성화**되는 구조.
  provider가 하나일 때는 드러나지 않던 문제였다.
- **개선 ①**: RAG 임베딩은 한국어 성능 때문에 bge-m3로 고정해야 하므로
  `spring.ai.model.embedding: ollama` 명시.

- **발견 ②**: 이어서 `openAiAudioSpeechModel` 생성 실패로 기동 중단.
- **진단 ②**: OpenAI 스타터가 Chat 외에 Audio Speech·Transcription·Image·Moderation
  오토컨피그를 함께 들여오는데, 이들은 우리 `ChatClientFactory`처럼 `ObjectProvider`+try-catch로
  감싸져 있지 않아 키가 없으면 컨텍스트 초기화 자체를 중단시킨다.
- **개선 ②**: 사용하지 않는 4개를 `spring.autoconfigure.exclude`로 제외.

- **발견 ③**: `.env`를 만들고 기동에 성공했는데 **키가 주입되지 않음**.
- **진단 ③**: Spring의 `SPRING_AI_OPENAI_API_KEY` → `spring.ai.openai.api-key` 완화 바인딩은
  **OS 환경변수에만** 적용되고 properties 파일 키에는 적용되지 않는다. `.env`의 해당 줄은
  이름이 특이한 무관한 속성으로 읽히고 있었다.
- **개선 ③**: yaml에 `api-key: ${SPRING_AI_OPENAI_API_KEY:}` 플레이스홀더 명시.
- **검증**: 셸 환경변수를 전혀 주지 않고 `.env`만으로 기동 → `Started BtllmApplication` 확인.
- **교훈**: **"설정 파일을 읽는 데 성공한 것"과 "값이 목적지 속성에 바인딩된 것"은 다른 문제다.**
  기동 성공만 보고 넘어갔다면 키가 빈 채로 실험을 돌려 잘못된 결론을 냈을 것이다.

## 5. LLM 품질 평가 파이프라인 — 이 프로젝트의 핵심 엔지니어링

LLM 애플리케이션은 "고쳤더니 좋아진 것 같다"가 통하지 않는다. 같은 질문에도 매번 다른 답이
나오고, 프롬프트 한 줄을 바꾸면 무관한 시나리오가 조용히 망가진다. 그래서 **개선보다 먼저
측정 체계를 만들었다.**

| 하네스 | 대상 | 판정 방식 |
|---|---|---|
| `ragAccuracyExperiment` | 청크 크기별 검색 Recall | 골든셋 35건, Recall@k |
| `ragGenerationQualityExperiment` | PDF 기반 최종 답변 품질 | 골든셋 8문항, 필수 사실·금지 오답·출처 정규식 |
| `localConversationQualityExperiment` | 정체성·기억·주제 전환·출력 계약 | 시나리오 4종, 반복 실행 지원 |
| `providerComparisonExperiment` | 동일 골든셋 모델 간 비교 | 위 판정기 재사용, provider만 교체 |

설계에서 신경 쓴 점:

- **판정기를 실험과 분리**해 단위 테스트로 검증한다(`RagAnswerEvaluatorTest`,
  `ConversationAnswerEvaluatorTest`). 평가 기준 자체가 틀리면 모든 수치가 무의미해진다.
- **자동 판정은 의도적으로 엄격하게** 유지하고, 의미 판단이 필요한 항목은 사람 검토 수치를
  따로 병기한다(예: 자동 12.5% / 사람 검토 37.5%). 반복 비교 가능성을 정확도보다 우선했다.
- **문항마다 보고서를 갱신**한다. 로컬 모델 실험은 8문항에 4분 이상 걸려 중단 위험이 커서,
  완료분을 잃지 않도록 했다.
- 실 Ollama·상용 API를 호출하는 실험은 **태그로 일반 테스트에서 격리**한다. 특히 provider 비교는
  실제 과금이 발생하므로 CI에서 절대 실행되지 않는다.

## 7. 가설이 틀렸고, 그 과정에서 진짜 병목을 찾은 사례

이 절은 **실패한 가설을 그대로 남긴 기록**이다. 개선 수치가 아니라 원인 규명 과정이 결과다.

### 가설

`overview-1`("이 문서가 어떤 사업인지 핵심만 설명해줘")은 재정렬 도입 후에도 실패했다.
당시 로그에서 모델이 만든 검색 질의가 `모두의 창업 프로젝트`처럼 짧아, 문서 제목이 반복 등장하는
조항 청크가 상위를 차지하고 사업 개요 청크는 후보 풀에 들어오지 못한 것으로 보였다.

→ **가설**: 개요형 질문은 문서 본문과 의미적으로 멀다. 색인 시점에 문서 전체를 요약한 청크를
추가하면 개요형 질의와 가까운 후보가 항상 존재하게 된다.

### 구현과 통제

`DocumentSummarizer`를 만들어 색인 시 문서당 LLM 1회로 개요 청크를 생성하고 함께 적재했다.
요약 실패가 본문 색인을 막지 않도록 예외를 흡수했다.

측정 도중 **평가 코퍼스가 바뀐 것을 발견**했다. 재색인 결과가 21청크·31,096자에서
38청크·206,147자로 늘어, 기존 기준선과 비교하면 무효였다. 그래서 **같은 38청크 코퍼스에서
기준선을 다시 측정**한 뒤 요약 청크만 추가하는 A/B로 통제했다.

| | 기준선(38청크) | 요약 청크 추가 후 |
|---|---:|---:|
| 문항 통과율 | 0.0% (0/8) | 0.0% (0/8) |
| 필수 사실 포함률 | 38.1% (8/21) | 33.3% (7/21) |
| 평균 응답시간 | 65.8s | 72.1s |

**효과 없음.** 오히려 소폭 하락(측정 편차 범위로 판단).

### 왜 효과가 없었는가 — 검색 단계 직접 진단

최종 답변만 보면 *(A) 요약 청크가 검색되지 않은 것*인지 *(B) 검색은 됐는데 모델이 못 쓴 것*인지
구분할 수 없다. 그래서 검색 단계만 들여다보는 진단 도구를 만들었다.

```
질의: "업로드한 ... 어떤 사업인지 핵심만 간략히 설명해줘"
  후보 1위 score=0.6446 [요약] [문서 개요] ...
  후보 2위 score=0.6265 [본문] 1 사업 개요 □ (사업목적) 참신한 아이디어 발굴·보육 ...
```

두 가지가 드러났다.

1. **요약 청크는 정상 검색된다.** 개요형 질의에서 1위, 짧은 질의에서 3위. 가설의 검색 전제는 맞았다.
2. **그런데 본문의 `1 사업 개요` 청크도 이미 1~2위로 검색되고 있었다.** 즉 **애초에 Recall 실패가
   아니었다.** 앞선 진단은 21청크 시절 코퍼스에서 내린 것이었고, 현재 코퍼스에서는 정답 근거가
   이미 상위에 올라와 있었다. 요약 청크는 이미 있는 근거를 중복시켰을 뿐이다.

### 그 과정에서 찾은 진짜 병목 — 컨텍스트 초과

진단 중 청크 크기가 눈에 띄어 실측했다.

| 항목 | 값 |
|---|---:|
| 본문 청크 평균 길이 | 5,425자 |
| 최대 길이 | 10,117자 |
| 청크당 추정 토큰 | 약 1,507 |
| **topK=3 근거 추정 토큰** | **약 4,521** |
| **설정된 `num_ctx`** | **4,096** |

**검색된 근거만으로 컨텍스트 창을 이미 초과한다.** 시스템 프롬프트와 질문, 도구 스키마는 계산에
넣지도 않았다. 모델은 검색이 찾아준 근거를 **끝까지 보지도 못한 채** 답하고 있었다.

이것으로 `overview-1`의 남은 실패 패턴(일반/기술트랙 8,000명, 로컬트랙 2,000명 같은 선정 규모
수치)이 설명된다. 여러 청크에 흩어진 사실을 모아야 하는 질문인데, 애초에 근거가 잘려 들어간다.

### 결론과 다음 조치

- 요약 청크는 **현재 코퍼스에서는 불필요한 중복**이다. 다만 짧은 질의에서 안정적으로 상위에
  잡히므로, 청크 구성이 다른 문서에서는 여전히 유효할 수 있어 기능은 유지하되 기본 활성 여부는
  컨텍스트 문제 해결 후 재평가한다.
- **다음 개선은 컨텍스트 예산 관리다.** 청크 크기 축소, `num_ctx` 상향(8GB VRAM에서 KV 캐시
  증가와 트레이드오프), 근거 길이 상한 중 무엇이 유효한지 같은 골든셋으로 비교한다.

### 이 사례에서 배운 것

**진단은 그것을 내린 시점의 데이터에만 유효하다.** "사업 개요 청크가 후보에 없다"는 관찰은
당시엔 사실이었지만 코퍼스가 바뀌자 더 이상 사실이 아니었고, 나는 그 낡은 진단 위에 기능을
하나 얹었다. 검색 단계를 직접 들여다보지 않았다면 "요약 청크를 넣었는데 왜 안 오르지"에서
멈췄을 것이다. **최종 지표가 움직이지 않을 때, 중간 단계를 관측 가능하게 만드는 것이
다음 가설보다 먼저다.**

## 8. 컨텍스트 예산 관리 — 이 프로젝트 최대 폭의 개선

### 발견

7장의 진단으로 병목이 특정됐다. 청크 크기 1500토큰 설정이 한국어 공고문에서 평균 5,425자
청크를 만들었고, `topK=3` 근거만 약 4,521토큰으로 `num_ctx` 4,096을 이미 초과하고 있었다.
검색이 정답을 찾아줘도 모델은 그 뒷부분을 보지 못했다.

### 진단 — 왜 1500이었나

청크 1500은 원래 **임베딩 호출 수를 줄이려는 최적화**였다(3-2). 당시 측정한 대가는
"Recall 11.4%p 하락"이었고, 그 판단은 문서 크기가 31,096자일 때 내려졌다. 문서가
206,147자로 커지자 **같은 설정이 전혀 다른 결과를 낳았다.** 청크 수는 늘지 않고
청크 하나하나가 비대해져, 검색 정확도가 아니라 컨텍스트 창을 압박하는 방향으로 작동했다.

즉 이 문제는 "잘못된 설정"이 아니라 **"입력 규모가 달라졌는데 함께 재검토되지 않은 설정"**이었다.

### 개선

청크 크기를 800토큰으로 낮추고, 값을 코드 상수가 아니라 설정값(`btllm.rag.chunk-size`)으로
분리했다. 색인 시점 파라미터라 변경하려면 재색인이 필요하고, 골든셋으로 크기별 효과를
비교하려면 코드 수정 없이 주입할 수 있어야 하기 때문이다.

재발 방지로 **분할 직후 평균 청크 길이를 로그로 남긴다.** 이번 문제의 핵심은 "설정한 토큰 수"와
"실제 문자 수"의 관계가 언어·문서마다 다르다는 것을 관측할 수단이 없었다는 데 있다.

### 검증 — 동일 문서·동일 골든셋 8문항

| 지표 | 청크 1500 (38청크) | **청크 800 (63청크)** |
|---|---:|---:|
| 문항 통과율 | 0.0% (0/8) | **50.0% (4/8)** |
| 필수 사실 포함률 | 38.1% (8/21) | **76.2% (16/21)** |
| 출처 표시율 | 100% | 100% |
| 평균 응답시간 | 65.8s | **50.6s** |
| 청크 평균 길이 | 5,425자 | 3,225자 |
| `topK=3` 근거 추정 토큰 | 4,521 (**초과**) | 2,687 (여유) |

- 통과율 **0% → 50%**, 사실 포함률 **2배**.
- **지연도 함께 23% 줄었다.** 컨텍스트가 짧아지면 프리필 연산이 줄어들기 때문으로, 품질과
  속도가 상충하지 않고 같이 개선된 드문 경우다.

### 이 결과의 의미 — 로컬 모델이 상용 모델 수준의 근거 활용도에 도달

3-4의 provider 비교에서 gpt-4o-mini의 필수 사실 포함률이 **76.2%**였다. 청크 크기를 고친
로컬 qwen3:8b가 **같은 76.2%**를 기록했다.

즉 **직전까지 "모델 체급 문제"로 분류했던 실패 상당수가 실제로는 컨텍스트 초과였다.**
`application-1`은 로컬 0/4 → **4/4**, `prize-1`은 0/2 → **2/2**로 뒤집혔다. GPT조차 실패해
"검색 문제"로 분류했던 `prize-1`까지 해결됐다.

이것은 **원인 분해가 완벽하지 않았음을 보여주는 결과이기도 하다.** provider 비교는 유효한
도구였지만, 두 모델이 *동일하게 잘린 근거*를 받고 있었다는 공통 조건까지는 드러내지 못했다.
상용 모델은 잘린 근거로도 더 잘 버텼을 뿐이다.

### 남은 실패

| 문항 | 상태 |
|---|---|
| `prize-1` | 필수 사실 2/2를 모두 포함했으나 금지 오답(일반/기술트랙 상금을 1억으로 서술)에 걸림 |
| `track-1` | 0/2 — 트랙별 지원 분야 구분 실패 |
| `registration-1` | 1/3 — 트랙별 사업자등록 시점 귀속 오류 |
| `overview-1` | 3/4 — 선정 규모 수치 일부 누락 |

남은 실패는 **여러 청크에 흩어진 사실을 트랙별로 올바르게 귀속시키는 문제**로 성격이 모인다.
`topK` 상향(컨텍스트 여유가 생겼으므로 이제 가능), `num_ctx` 8192, 표 구조 보존 청킹이 다음 후보다.

## 9. Provider 재비교 — 프로젝트의 전제가 뒤집힌 지점

### 왜 다시 쟀는가

3-4의 provider 비교는 **청크 1500 시절에 측정한 값**이다. 8장에서 컨텍스트 초과를 고쳤으므로
그 비교는 더 이상 유효하지 않다. 낡은 수치를 근거로 "로컬은 상용보다 한참 떨어진다"는 서술을
유지하는 것은 이 프로젝트가 지켜온 측정 원칙에 어긋난다. 그래서 **동일 조건에서 다시 쟀다.**

### 1차 결과와 그 함정

먼저 각 provider 1회씩 실행했더니 **62.5% 대 62.5%로 동률**, 사실 포함률은 로컬이 81.0%로
상용(76.2%)보다 높게 나왔다. "로컬이 상용을 따라잡았다"고 쓰고 싶어지는 결과다.

**그러나 이 프로젝트의 원칙상 단발 결과로 그렇게 주장할 수 없다.** 로컬 모델은 같은 골든셋에서
0%~62.5%까지 흔들린 전력이 있다. 그래서 하네스에 반복 실행을 추가하고 **3회씩 다시 쟀다.**

### 3회 반복 결과 — 1차 결론은 부분적으로 틀렸다

| Provider / 모델 | 통과율 (24회) | 사실 포함률 | 평균 지연 | p95 |
|---|---:|---:|---:|---:|
| ollama / qwen3:8b | 50.0% (12/24) | **77.8% (49/63)** | 88.9s | **188.6s** |
| openai / gpt-4o-mini | **58.3% (14/24)** | **77.8% (49/63)** | 4.9s | 7.1s |

- **사실 포함률은 소수점까지 동일한 77.8%.** 근거 활용도에서는 진짜로 동등하다.
- **통과율은 상용이 8.3%p 앞선다.** 1차의 "동률"은 로컬이 좋은 회차를, 상용이 나쁜 회차를
  뽑은 우연이었다. 통과 조건이 *사실 100% + 금지 오답 0건*이므로, 같은 양의 사실을 뽑고도
  **로컬이 오답을 더 자주 섞는다**는 뜻이다.

### 예상과 반대였던 것 — 편차는 로컬이 더 작았다

| Provider | #1 | #2 | #3 | 범위 |
|---|---:|---:|---:|---:|
| ollama / qwen3:8b | 50.0% | 50.0% | 50.0% | **0.0%p** |
| openai / gpt-4o-mini | 50.0% | 62.5% | 62.5% | 12.5%p |

반복 실행을 도입한 명분은 "로컬이 불안정하니 확인하자"였는데, 실제로는 **로컬이 3회 모두
정확히 50.0%로 완전히 안정적**이었고 상용 쪽이 흔들렸다. 로컬의 과거 편차(0%~62.5%)는
모델의 비결정성이 아니라 **그 사이에 우리가 바꾼 파이프라인 설정 때문**이었던 것이다.

### 문항별 안정성 — 단발이 오도했던 지점이 드러났다

| 문항 | qwen3:8b | gpt-4o-mini |
|---|---|---|
| round-general-1 | ✅ 3/3회 | ✅ 3/3회 |
| eligibility-1 | ✅ 3/3회 | ✅ 3/3회 |
| application-1 | ✅ 3/3회 | ✅ 3/3회 |
| round-local-1 | ⚠️ 2/3회 | ✅ 3/3회 |
| overview-1 | ⚠️ 1/3회 | ⚠️ 2/3회 |
| **track-1** | ❌ 0/3회 | ❌ 0/3회 |
| **registration-1** | ❌ 0/3회 | ❌ 0/3회 |
| **prize-1** | ❌ 0/3회 (사실 6/6) | ❌ 0/3회 (사실 6/6) |

1차 실행에서 `overview-1`은 양쪽 모두 ✅였지만, 실제로는 **로컬 1/3회·상용 2/3회의 간헐 통과**다.
단발 결과만 봤다면 이 문항을 "해결됨"으로 분류하고 회귀 감시에서 빼버렸을 것이다.

반면 **`track-1`·`registration-1`·`prize-1`은 두 모델 모두 3회 전부 실패했다.**
6회씩 총 12회 시도에서 단 한 번도 통과하지 못했으므로, **모델 교체로 풀리는 문제가 아님이
확정됐다.** 앞으로 검색·청킹 개선의 효과는 이 3문항으로 판정하면 된다.

`prize-1`은 성격이 조금 다르다. **필수 사실 6/6을 모두 포함하고도 3회 전부 실패**했다.
금지 오답 패턴(일반/기술트랙 상금을 1억으로 서술)에 걸린 것으로, 모델이 트랙별 수치를
교차 귀속시키는 문제이거나 골든셋 판정 기준 자체를 재검토해야 하는 사례다.

### 이 결과가 프로젝트에 갖는 의미

출발 질문은 *"개인 PC의 로컬 모델이 정말 쓸 만한 수준이 될 수 있는가"*였다.
중간 측정만 보면 답은 "아니오"에 가까웠다(25% vs 62.5%). 반복 측정까지 마친 지금의 답은
**"근거 활용도는 동등하고, 오답률과 속도가 남는다"**이다.

| 축 | 판정 |
|---|---|
| 근거에서 사실을 뽑아내는 능력 | **동등** (77.8% vs 77.8%) |
| 오답 없이 답하는 안정성 | 상용 우위 (58.3% vs 50.0%) |
| 응답 속도 | 상용 압도 (평균 18배, p95 26배) |
| 비용·프라이버시 | 로컬 우위 (과금 없음, 문서 외부 전송 없음) |

이 격차의 대부분은 모델의 한계가 아니라 **우리가 근거를 잘라서 넣고 있었기 때문**이었고,
그것을 걷어내자 남은 것은 위 네 줄로 정리됐다. 지연은 8GB VRAM의 GPU 서빙 슬롯 1개라는
구조적 제약에서 온다(2-5).

**이제 로컬 대 상용은 우열이 아니라 트레이드오프로 서술할 수 있다.** 민감 문서와 비용 제약이
있는 사용에는 로컬이 실제로 쓸 만하고, 응답성이 중요한 사용에는 상용이 맞다.

### 이 장에서 배운 것

1. **낡은 측정값으로 아키텍처를 결정하면 안 된다.** 재측정하지 않고 청크 1500 시절 수치를
   뒀다면 "품질이 필요하면 상용으로 라우팅"이라는 잘못된 설계 결론에 도달했을 것이다.
2. **단발 결과는 유리한 방향으로도 오도한다.** 1차 실행의 "동률·로컬 우위"는 우연이었고,
   내가 원하던 결론이었기에 더 위험했다. 반복 측정이 그것을 걸러냈다.
3. **가정은 반대 방향으로도 틀린다.** "로컬이 불안정할 것"이라는 전제로 반복을 도입했는데,
   정작 편차는 상용 쪽이 컸다. 로컬의 과거 편차는 모델이 아니라 그 사이 바뀐 우리 설정 탓이었다.
