# 포트폴리오 개선 작업 로그

이 문서는 BTLLM을 포트폴리오 수준으로 개선하면서 발견한 문제와 의사결정 과정을 기록한다.
각 항목은 `발견 → 진단 → 해결 → 검증 → 남은 한계` 순서로 작성한다.

## 2026-08-26 — 품질 게이트 복구

### 발견

이전 기능 작업 6개 커밋을 인수한 직후 기본 품질 게이트를 실행했다.

- 백엔드 `gradlew test`: 테스트 코드 컴파일 오류 2건
- 프론트엔드 `npm run lint`: React Hooks 규칙 오류 6건
- 프론트엔드 `npm run build`: 성공

기능 검증 위주로 작업하면서 Repository API 변경과 테스트 코드가 함께 갱신되지 않았고,
WebSocket 재연결 구현에서 React 렌더 단계에 ref를 직접 변경하고 있었다.

### 진단

#### 백엔드

대화 이력 순서를 안정화하려고 Repository 메서드를
`findByChatRoomIdOrderByCreatedAtAscIdAsc`로 변경했지만, 서비스 테스트 2곳은 삭제된
`findByChatRoomIdOrderByCreatedAtAsc`를 계속 호출했다. 운영 코드가 아니라 테스트 코드의
API 동기화 누락이어서 `compileTestJava` 단계에서 실패했다.

#### 프론트엔드

React 19 ESLint 규칙이 다음 패턴을 탐지했다.

- `useWebSocket`: 렌더 중 callback ref 4개 변경
- `ChatPage`: 렌더 중 `sendMessage` ref 변경 1건
- `ChatPage`: 마운트 effect에서 첫 메시지 state를 동기 변경 1건

콜백 ref는 WebSocket effect의 불필요한 재실행을 막는 데 필요하지만, 렌더 중 `.current`를
변경하면 React의 순수 렌더링 가정을 깨뜨린다. 첫 메시지는 props만으로 결정되므로 effect가
아니라 state/ref의 지연 초기값으로 표현할 수 있었다.

### 해결

- 테스트 mock을 실제 Repository 메서드명과 동기화
- callback ref와 `sendMessage` ref 갱신을 의존성이 명시된 `useEffect`로 이동
- 첫 사용자 메시지를 `useState` 지연 초기값으로 구성
- WebSocket 연결 후 보낼 첫 메시지는 `useRef(initialMessage)`로 초기화
- 기존 방의 저장 이력만 마운트 effect에서 비동기로 조회

WebSocket의 재연결 조건과 메시지 큐 동작은 변경하지 않고 React 생명주기 규칙만 바로잡았다.

### 검증

| 품질 게이트 | 수정 전 | 수정 후 |
|---|---:|---:|
| 백엔드 테스트 컴파일 | 오류 2건 | 오류 0건 |
| 백엔드 테스트 | 실행 불가 | 21건 통과, 실패 0건 |
| 프론트 lint | 오류 6건 | 오류 0건 |
| 프론트 프로덕션 빌드 | 성공 | 성공 |

백엔드 첫 실행은 샌드박스 네트워크 제한 때문에 Gradle 배포본 다운로드에 실패했다.
동일 명령을 네트워크가 허용된 환경에서 재실행해 코드 실패와 실행 환경 실패를 분리했다.

### 남은 한계

- 현재 검증은 단위 테스트·정적 분석·프로덕션 번들 생성까지다.
- WebSocket 재연결과 첫 메시지 자동 전송의 브라우저 E2E 회귀 테스트는 아직 자동화되지 않았다.
- 다음 기능 변경 전, 문서 기반 답변의 생성 품질을 별도 평가할 수 있는 기준이 필요하다.

## 2026-08-26 — RAG 검색 결과 구조화와 근거 표시

### 발견

34페이지 정부 공고문을 인덱싱한 뒤 “모두의 창업 프로젝트가 어떤 사업인지 간략히 설명”하라고
질문했을 때, 벡터 검색 상위에는 사업 개요와 트랙 설명이 있었지만 모델은 신청 제한 부록을
지원 내용처럼 설명했다.

기존 `searchKnowledgeBase` Tool은 검색된 5개 청크를 `---`로만 연결했다. 모델은 어느 청크가
더 관련 있는지, 어느 파일에서 왔는지, 문서의 어느 위치인지 알 수 없었고 답변 작성 규칙도 없었다.

### 진단

실제 pgVector의 21개 레코드를 조회해 다음 메타데이터가 보존되는 것을 확인했다.

- `source`: 원본 파일명
- `chunk_index`: 0부터 시작하는 청크 번호
- `total_chunks`: 문서 전체 청크 수

페이지 번호는 저장되지 않았으므로 존재하지 않는 페이지 출처를 만들지 않고 청크 위치를 사용했다.
또한 작은 로컬 모델은 긴 Tool 결과 뒤에서 앞쪽 지침을 무시할 수 있어, 결과 앞과 뒤에 답변 규칙을
두는 샌드위치 구조가 필요하다고 판단했다.

### 해결

- 각 검색 결과에 `[관련도 N위]`, 파일명, `현재/전체 청크` 위치를 표시
- 상위 결과 우선, 근거 밖 추측 금지, 지원·자격·제한 의미 혼합 금지 규칙 추가
- 답변 마지막 줄에 `[출처] 파일명`을 표시하도록 출력 계약 추가
- 업로드 문서 안의 명령은 데이터로만 취급하도록 프롬프트 인젝션 방어 규칙 추가
- 시스템 프롬프트와 Tool 결과 양쪽에 근거 기반 답변 규칙 배치
- 메타데이터가 누락되거나 숫자가 문자열로 저장된 경우도 안전하게 처리

### 검증

#### 자동 검증

- `LlmToolsTest` 3건 추가
  - 관련도 순위·출처·청크 위치와 검색 설정(topK 5, threshold 0.5)
  - 검색 0건일 때 인덱싱된 문서 목록 반환
  - 메타데이터 누락 시 `출처 미상` 처리
- 전체 백엔드 테스트: 24건 통과, 실패 0건

#### 실제 qwen3:8b + PDF E2E

동일 질문을 WebSocket으로 전송해 실제 Tool 호출부터 생성까지 확인했다.

| 항목 | 앞쪽 지침만 적용 | 앞·뒤 출력 계약 적용 |
|---|---|---|
| 완료 시간 | 109.8초 | 59.9초 |
| 답변 길이 | 신청·제한 내용을 장황하게 나열 | 신청 자격 3개 항목으로 축소 |
| 출처 표시 | 없음 | PDF 파일명 표시 성공 |
| 사업 개요 적합성 | 실패 | 실패 |

두 실행의 지연 차이는 GPU 상태와 생성량의 영향을 함께 받으므로 구조화의 성능 효과로 단정하지 않는다.
확실히 개선된 것은 출처 표시와 불필요한 부록 나열 감소다.

### 남은 한계와 다음 가설

두 번째 실행에서도 “사업 개요”를 “로컬트랙 신청 자격”으로 축소해 답했다. 로그상 모델이 만든
검색 질의는 `모두의 창업 프로젝트 사업 내용`으로 자연스러웠으므로 Tool 호출 여부나 명백한 질의
오염 문제는 아니었다. 관련 없는 하위 청크까지 포함하는 topK 5와 4096 컨텍스트 안에서의 정보
선택 실패가 다음 핵심 가설이다.

따라서 이번 변경은 **출처 추적성과 답변 계약 개선**으로 범위를 한정한다. 사업 개요 정확도 문제는
다음 단계에서 topK와 컨텍스트 크기를 분리 비교해 해결한다.

## 2026-08-26 — 검색량 축소로 RAG distractor 억제

### 발견

검색 결과 구조화 후에도 “어떤 사업인지 핵심만 설명”이라는 질문을 로컬트랙 신청 자격으로
잘못 축소했다. Tool 호출 로그의 검색 질의는 `모두의 창업 프로젝트 사업 내용`으로 정상적이어서
질의 재작성보다 검색 결과 안의 정보 선택 문제를 의심했다.

### 진단

동일 질의를 bge-m3로 임베딩하고 pgVector 상위 5개를 직접 조회했다.

| 순위 | 유사도 | 내용 판정 |
|---:|---:|---|
| 1 | 0.653 | 트랙·선정 규모·토너먼트 구조 — 핵심 근거 |
| 2 | 0.622 | 사업 목적·지원 대상·트랙 구분 — 핵심 근거 |
| 3 | 0.569 | 신청 제한·재도전 우대 — 부분 관련 |
| 4 | 0.568 | 참여 제외·동시 수행 제한 — distractor |
| 5 | 0.560 | 중복 참여 불가 사업 목록 부록 — 강한 distractor |

검색기는 정답 청크를 1~2위에 올렸지만 topK 5가 하위 부록까지 생성 모델에 전달했다.
qwen3:8b는 상위 순위보다 구체적인 목록을 따라가며 질문 의도를 잃었다.

### 전략

8GB VRAM 환경에서 `num_ctx 8192`를 먼저 적용하면 KV cache 증가로 TTFT와 동시성이 악화될 수 있다.
따라서 한 번에 하나의 변수만 바꾸는 원칙으로 컨텍스트는 4096에 두고 topK만 5에서 3으로 줄였다.

운영 Tool과 실험 하네스가 다른 값을 사용하지 않도록 `RagSearchSettings`를 단일 기준점으로 추가했다.
Ollama 컨텍스트는 모델 기본값에 기대지 않고 4096으로 명시해 실행 환경의 재현성도 확보했다.

### 해결 및 검증

| 항목 | topK 5 | topK 3 |
|---|---:|---:|
| 검색 본문 문자 수 | 7,540자 | 4,616자 |
| 컨텍스트 감소 | 기준 | 38.8% 감소 |
| 사업 개요 적합성 | 실패 | 핵심 관련성 회복 |
| 출처 표시 | 성공 | 성공 |
| E2E 완료 시간 | 59.9초 | 76.0초 |

topK 3 답변은 다음 핵심을 포함했다.

- 전 국민 대상 창업 도전 사업
- 일반/기술트랙 8,000명, 로컬트랙 2,000명
- 창업활동자금·AI 솔루션·멘토링·GPU·MVP·사업화 지원
- 최대 5억원 상금과 공식 신청 홈페이지

완료 시간은 답변 생성량과 GPU 상태 영향을 받으므로 topK 축소의 속도 개선 근거로 사용하지 않는다.
대신 검색 본문 문자 수 38.8% 감소를 직접적인 컨텍스트 절감 수치로 사용한다.

### 남은 한계

답변은 “2R 진출 시 사업자등록 필수”를 두 트랙에 공통인 것처럼 표현했다. 원문은
일반/기술트랙 3R, 로컬트랙 2R로 서로 다르다. 핵심 관련성은 회복했지만 세부 조건의 트랙 귀속에는
오류가 남아 있어 완전 성공으로 평가하지 않는다.

단일 질문에 계속 맞추면 과적합될 수 있으므로 추가 프롬프트 수정은 중단한다. 다음 단계에서 실제
PDF 기반 다문항 생성 품질 평가셋을 먼저 만들고, 트랙별 조건·수치 귀속 오류를 재현 가능한 지표로
측정한 뒤 개선한다.

## 2026-08-26 — PDF 기반 RAG 생성 품질 평가셋 구축

### 발견

기존 RAG 실험은 검색 Recall만 측정했다. 실제 PDF 테스트에서는 정답 청크가 검색돼도 모델이
핵심을 누락하거나 트랙별 조건을 잘못 연결했으므로, 검색 지표만으로 최종 사용자 답변 품질을
보장할 수 없었다.

### 평가 설계

34페이지 정부 공고문에서 사용자가 실제로 물을 만한 8개 범주를 선정했다.

- 사업 개요, 트랙 차이
- 일반/기술 및 로컬 라운드별 인원
- 트랙별 사업자등록 시점과 최대 상금
- 예비·기창업자 신청 자격
- 신청 기간·마감 시각·사이트

각 문항은 정규식 기반 필수 사실과 금지 오답을 가지며, 통과 조건을 다음처럼 엄격하게 정의했다.

1. 필수 사실 100% 포함
2. 금지 오답 0건
3. `[출처]` 표시

실제 `ChatClient + Tool Calling + pgVector + qwen3:8b` 전체 경로를 순차 실행하고, 필수 사실 포함률,
문항 통과율, 출처 표시율, 평균·p95 응답 시간을 자동 보고서로 생성한다. 일반 테스트에서는
외부 의존 실험을 제외하고 `ragGenerationQualityExperiment` 태스크로만 실행하게 분리했다.

### 평가 도구 자체에서 발견한 문제

#### 1. 사용하지 않는 외부 provider가 실험 기동을 차단

첫 실행은 문항 처리 전에 Anthropic API 키가 없어 ApplicationContext가 실패했다. 팩토리 내부에서
예외를 흡수해도 자동설정 빈의 선생성까지 막지는 못했다. Ollama 전용 실험 태스크에 외부 통신을
하지 않는 더미 키를 주입해 멀티 provider 빈 생성 조건만 충족하도록 수정했다.

#### 2. 8분 실행 후 보고서 포맷 오류

두 번째 실행은 8문항을 모두 생성했지만 마지막 보고서의 p95 `long` 값을 `%.1f`로 포맷해
`IllegalFormatConversionException`이 발생했다. Gradle XML에서 판정과 지연은 복구했지만 상세 답변은
인메모리 ChatMemory와 함께 사라졌다.

- 원인: `p95LatencyMs / 1000`이 정수형인데 부동소수점 포맷 사용
- 수정: `p95LatencyMs / 1000.0`으로 변환
- 재발 방지: 문항 하나가 끝날 때마다 보고서를 증분 저장

평가 대상 코드뿐 아니라 **평가 하네스 자체도 실패 복구 가능하게 설계해야 한다**는 교훈을 얻었다.

### 최종 실행 결과

실행 시간 8분 25초, 8문항 순차 평가 기준이다.

| 지표 | 자동 엄격 기준 |
|---|---:|
| 문항 통과율 | 12.5% (1/8) |
| 필수 사실 포함률 | 28.6% (6/21) |
| 출처 표시율 | 100% (8/8) |
| 평균 응답시간 | 60.4초 |
| p95 응답시간 | 87.1초 |

상세 사람 검토에서 `track-1`과 `eligibility-1`은 의미상 정답이지만 표현이 정규식과 달라
실패 처리된 것을 확인했다. 사람 검토 보정 기준은 문항 통과율 37.5%(3/8), 필수 사실 포함률
38.1%(8/21)다. 자동 지표는 반복 비교용 엄격 기준으로 그대로 보존한다.

### 반복 실행에서 확인한 변동성

보고서 오류가 난 직전 실행의 복구 가능 지표와 최종 실행을 비교했다.

| 항목 | 직전 실행 | 최종 실행 |
|---|---:|---:|
| 자동 통과 | 2/8 | 1/8 |
| 필수 사실 | 11/21 | 6/21 |
| 출처 표시 | 8/8 | 8/8 |
| 평균 지연 | 61.9초 | 60.4초 |
| p95 지연 | 100.4초 | 87.1초 |

동일 설정에서도 일반/기술 라운드와 로컬 라운드의 통과 결과가 서로 뒤바뀌었다. 반면 사업자등록은
두 번 모두 1/3, 상금은 0/2, 신청 정보는 0/4로 실패해 안정적으로 취약한 영역이 드러났다.

### 결론과 다음 개선 후보

- 출처 계약은 2회 총 16답변에서 100% 유지돼 안정적이다.
- 작은 모델의 Tool 검색 질의와 사실 선택은 비결정적이며 단발성 성공으로 품질을 주장할 수 없다.
- topK를 줄여 개요 질문의 distractor는 완화했지만, 세부 수치 질문은 threshold 0.5에서 검색 적중이
  1~2건으로 줄거나 필요한 표 정보를 놓친다.
- 다음 RAG 개선은 전역 topK 재조정보다 질문 유형별 검색 전략, 표 구조 보존, 반복 평가를 기준으로
  해야 한다.

## 2026-08-26 — 로컬 모델 대기 UX와 스트리밍 Markdown 개선

### 문제와 근거

PDF 생성 품질 평가에서 qwen3:8b의 평균 응답 시간은 60.4초, p95는 87.1초였다. 기존 화면은
요청 직후 빈 `TOKEN`을 연결 신호로 재사용해 “서버가 요청을 받았는지”, “첫 토큰을 기다리는지”,
“답변을 생성 중인지”를 구분하지 못했다. 사용자는 긴 정상 처리도 멈춤이나 전송 실패로 오해할 수 있었다.

답변 영역도 기본 Markdown 스타일에만 의존해 표의 가로 스크롤, 코드 언어 표시·복사, 긴 문단의
여백이 부족했다. 포트폴리오 데모에서는 모델 성능뿐 아니라 기다리는 과정과 결과를 읽는 경험도
완성도의 일부라고 판단했다.

### 프로토콜과 화면 개선

- 연결 확인 `READY`, 요청 접수 `QUEUED`, 내용 스트림 `TOKEN`을 분리했다.
- `QUEUED` 수신 즉시 서버 접수 문구, 경과 시간, 10초 이후 로컬 모델 지연 안내를 표시했다.
- 첫 내용 토큰부터는 입력창 문구를 `답변 생성 중...`으로 바꿔 처리 단계를 구분했다.
- 답변 전용 `MarkdownMessage`를 추출해 제목·문단·목록·인용문 여백을 정리했다.
- 표는 테두리와 가로 스크롤을 적용하고, 코드 블록에는 언어명과 복사 피드백을 추가했다.
- 시스템 프롬프트에 Markdown 블록·표 행·코드 블록의 실제 개행 규칙을 명시했다.

### 브라우저 E2E에서 발견한 숨은 원인

첫 실시간 테스트에서는 제목, 목록, 표가 한 줄로 붙었지만 같은 답변을 새로고침하면 정상적으로
렌더링됐다. 이 차이로 모델 원문이나 CSS보다 **실시간 전송 경로와 저장 경로의 불일치**를 의심했다.

`TokenTrackingAdvisor`는 모든 청크를 저장하는 반면 WebSocket 핸들러는 `text.isBlank()`인 청크를
버리고 있었다. Ollama가 Markdown 줄바꿈을 독립적인 공백 청크로 보내면 실시간 화면에서만 개행이
사라지는 구조였다. 필터를 `isEmpty()`로 좁혀 내용이 없는 청크만 제외하고 줄바꿈은 보존했다.

### 검증

격리된 로컬 QA 계정에서 제목, 목록, 표, JavaScript 코드 블록을 요구하는 실제 qwen3:8b 요청을
두 차례 실행했다.

| 검증 항목 | 결과 |
|---|---|
| 요청 접수 상태 | 전송 약 1.5초 후 `QUEUED` 문구와 경과 시간 확인 |
| 최종 응답 | 약 25.2초 후 제목·목록·표·코드 블록이 스트리밍 화면에서 정상 분리 |
| 저장 이력 | 새로고침 후에도 동일한 Markdown 구조 유지 |
| 코드 복사 | 클릭 후 `복사됨` 피드백 확인 |
| 백엔드 테스트 | 29건 통과, 실패·오류 0건 |
| 프론트엔드 정적 검증 | ESLint 및 TypeScript/Vite 프로덕션 빌드 통과 |

이번 문제는 “Markdown CSS 보강”만으로는 해결되지 않았다. 스트리밍 중 화면과 저장 후 화면을
비교한 것이 공백 청크 손실을 발견하는 결정적 단서였고, 프로토콜 수준에서 수정해 모든 Markdown
렌더러가 동일한 원문을 받도록 만들었다.

## 2026-08-26 — 로컬 모델 대화 품질 기준선 구축

### 문제

PDF RAG 평가는 문서 사실 정확도만 측정한다. 실제 사용자 테스트에서 나타난 서비스 정체성 오류,
이전 대화 기억, 문서 대화 이후의 주제 전환, Markdown 출력 계약은 기존 지표로 재현할 수 없었다.
생성 파라미터나 모델을 바꿔도 같은 질문으로 비교하지 않으면 개선 여부를 판단할 근거가 없었다.

### 평가 설계

다음 네 시나리오를 JSON 평가셋과 정규식 판정기로 구성했다.

- 서비스가 자신을 BTLLM으로 소개하고 모델 제작사를 사칭하지 않는가
- 같은 대화 안에서 사용자가 지정한 코드명을 기억하는가
- 창업 지원 배경을 들은 뒤 자격 설명을 반복하지 않고 1인 개발 아이디어로 전환하는가
- 정확히 요구한 Markdown 표·사용자·수익 모델 계약을 따르는가

모델, temperature, top-p, top-k, Thinking, 컨텍스트, 최대 출력 토큰, 반복 횟수를 환경변수로
주입할 수 있게 해 이후 실험이 같은 코드와 평가셋을 사용하도록 했다. 실제 Ollama를 호출하는 태스크는
별도 태그로 격리해 일반 테스트와 CI에서는 실행하지 않는다. 장시간 실행이 중단돼도 완료된 문항을
잃지 않도록 문항마다 보고서를 갱신한다.

### 현재 Qwen3 8B 기준선

설정은 `temperature=0.3`, `top_p=0.8`, `top_k=20`, Thinking 비활성, `num_ctx=4096`이다.

| 지표 | 결과 |
|---|---:|
| 자동 시나리오 통과율 | 0.0% (0/4) |
| 요구사항 충족률 | 88.9% (8/9) |
| 평균 지연 | 4.6초 |
| p95 지연 | 11.2초 |

### 발견

0%라는 결과만 보면 모델 이해력이 전부 실패한 것처럼 보이지만 상세 응답은 다른 원인을 보여줬다.

- 단기 기억은 `보라돌이`를 정확히 회상했다.
- 주제 전환 후에는 자격요건을 반복하지 않고 1인·8주·MVP 조건의 아이디어 3개를 제시했다.
- Markdown 표와 대상 사용자·수익 모델도 모두 충족했다.
- 그러나 모든 일반 답변에 `[출처]` 또는 `[출처] 사용자 제공 정보`를 붙였다.
- 정체성 질문에는 일반 AI 어시스턴트라고 답했지만 BTLLM이라는 서비스 이름은 알지 못했다.

즉 이번 기준선은 **작은 모델의 이해 실패와 시스템 프롬프트 정책 오류를 분리**했다. 현재 가장 큰
공통 실패 원인은 모델 체급보다 “사용한 문서 파일명을 항상 출처로 표시”한다는 조건이 비-RAG 답변까지
일반화된 것이다. 다음 단계에서는 출처 계약과 서비스 정체성을 먼저 바로잡은 뒤 동일 평가를 반복하고,
그 후 생성 파라미터와 Qwen3.5 모델을 비교한다.
