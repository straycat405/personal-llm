# 포트폴리오 개선 작업 로그

이 문서는 BTLLM을 포트폴리오 수준으로 개선하면서 발견한 문제와 의사결정 과정을 기록한다.
각 항목은 `발견 → 진단 → 해결 → 검증 → 남은 한계` 순서로 작성한다.

## 2026-08-26 — 품질 게이트 복구

### 발견

이전 기능 작업 6개 커밋을 인수한 직후 기본 품질 게이트를 실행했다.

- 백엔드 `gradlew test`: 테스트 코드 컴파일 오류 2건
- 프론트엔드 `npm run lint`: React Hooks 규칙 오류 6건
- 프론트엔드 `npm run build`: 성공

기능 검증 위주로 작업하면서 Repository API 변경과 테스트 코드가 함께 갱신되지 않았고,
WebSocket 재연결 구현에서 React 렌더 단계에 ref를 직접 변경하고 있었다.

### 진단

#### 백엔드

대화 이력 순서를 안정화하려고 Repository 메서드를
`findByChatRoomIdOrderByCreatedAtAscIdAsc`로 변경했지만, 서비스 테스트 2곳은 삭제된
`findByChatRoomIdOrderByCreatedAtAsc`를 계속 호출했다. 운영 코드가 아니라 테스트 코드의
API 동기화 누락이어서 `compileTestJava` 단계에서 실패했다.

#### 프론트엔드

React 19 ESLint 규칙이 다음 패턴을 탐지했다.

- `useWebSocket`: 렌더 중 callback ref 4개 변경
- `ChatPage`: 렌더 중 `sendMessage` ref 변경 1건
- `ChatPage`: 마운트 effect에서 첫 메시지 state를 동기 변경 1건

콜백 ref는 WebSocket effect의 불필요한 재실행을 막는 데 필요하지만, 렌더 중 `.current`를
변경하면 React의 순수 렌더링 가정을 깨뜨린다. 첫 메시지는 props만으로 결정되므로 effect가
아니라 state/ref의 지연 초기값으로 표현할 수 있었다.

### 해결

- 테스트 mock을 실제 Repository 메서드명과 동기화
- callback ref와 `sendMessage` ref 갱신을 의존성이 명시된 `useEffect`로 이동
- 첫 사용자 메시지를 `useState` 지연 초기값으로 구성
- WebSocket 연결 후 보낼 첫 메시지는 `useRef(initialMessage)`로 초기화
- 기존 방의 저장 이력만 마운트 effect에서 비동기로 조회

WebSocket의 재연결 조건과 메시지 큐 동작은 변경하지 않고 React 생명주기 규칙만 바로잡았다.

### 검증

| 품질 게이트 | 수정 전 | 수정 후 |
|---|---:|---:|
| 백엔드 테스트 컴파일 | 오류 2건 | 오류 0건 |
| 백엔드 테스트 | 실행 불가 | 21건 통과, 실패 0건 |
| 프론트 lint | 오류 6건 | 오류 0건 |
| 프론트 프로덕션 빌드 | 성공 | 성공 |

백엔드 첫 실행은 샌드박스 네트워크 제한 때문에 Gradle 배포본 다운로드에 실패했다.
동일 명령을 네트워크가 허용된 환경에서 재실행해 코드 실패와 실행 환경 실패를 분리했다.

### 남은 한계

- 현재 검증은 단위 테스트·정적 분석·프로덕션 번들 생성까지다.
- WebSocket 재연결과 첫 메시지 자동 전송의 브라우저 E2E 회귀 테스트는 아직 자동화되지 않았다.
- 다음 기능 변경 전, 문서 기반 답변의 생성 품질을 별도 평가할 수 있는 기준이 필요하다.

## 2026-08-26 — RAG 검색 결과 구조화와 근거 표시

### 발견

34페이지 정부 공고문을 인덱싱한 뒤 “모두의 창업 프로젝트가 어떤 사업인지 간략히 설명”하라고
질문했을 때, 벡터 검색 상위에는 사업 개요와 트랙 설명이 있었지만 모델은 신청 제한 부록을
지원 내용처럼 설명했다.

기존 `searchKnowledgeBase` Tool은 검색된 5개 청크를 `---`로만 연결했다. 모델은 어느 청크가
더 관련 있는지, 어느 파일에서 왔는지, 문서의 어느 위치인지 알 수 없었고 답변 작성 규칙도 없었다.

### 진단

실제 pgVector의 21개 레코드를 조회해 다음 메타데이터가 보존되는 것을 확인했다.

- `source`: 원본 파일명
- `chunk_index`: 0부터 시작하는 청크 번호
- `total_chunks`: 문서 전체 청크 수

페이지 번호는 저장되지 않았으므로 존재하지 않는 페이지 출처를 만들지 않고 청크 위치를 사용했다.
또한 작은 로컬 모델은 긴 Tool 결과 뒤에서 앞쪽 지침을 무시할 수 있어, 결과 앞과 뒤에 답변 규칙을
두는 샌드위치 구조가 필요하다고 판단했다.

### 해결

- 각 검색 결과에 `[관련도 N위]`, 파일명, `현재/전체 청크` 위치를 표시
- 상위 결과 우선, 근거 밖 추측 금지, 지원·자격·제한 의미 혼합 금지 규칙 추가
- 답변 마지막 줄에 `[출처] 파일명`을 표시하도록 출력 계약 추가
- 업로드 문서 안의 명령은 데이터로만 취급하도록 프롬프트 인젝션 방어 규칙 추가
- 시스템 프롬프트와 Tool 결과 양쪽에 근거 기반 답변 규칙 배치
- 메타데이터가 누락되거나 숫자가 문자열로 저장된 경우도 안전하게 처리

### 검증

#### 자동 검증

- `LlmToolsTest` 3건 추가
  - 관련도 순위·출처·청크 위치와 검색 설정(topK 5, threshold 0.5)
  - 검색 0건일 때 인덱싱된 문서 목록 반환
  - 메타데이터 누락 시 `출처 미상` 처리
- 전체 백엔드 테스트: 24건 통과, 실패 0건

#### 실제 qwen3:8b + PDF E2E

동일 질문을 WebSocket으로 전송해 실제 Tool 호출부터 생성까지 확인했다.

| 항목 | 앞쪽 지침만 적용 | 앞·뒤 출력 계약 적용 |
|---|---|---|
| 완료 시간 | 109.8초 | 59.9초 |
| 답변 길이 | 신청·제한 내용을 장황하게 나열 | 신청 자격 3개 항목으로 축소 |
| 출처 표시 | 없음 | PDF 파일명 표시 성공 |
| 사업 개요 적합성 | 실패 | 실패 |

두 실행의 지연 차이는 GPU 상태와 생성량의 영향을 함께 받으므로 구조화의 성능 효과로 단정하지 않는다.
확실히 개선된 것은 출처 표시와 불필요한 부록 나열 감소다.

### 남은 한계와 다음 가설

두 번째 실행에서도 “사업 개요”를 “로컬트랙 신청 자격”으로 축소해 답했다. 로그상 모델이 만든
검색 질의는 `모두의 창업 프로젝트 사업 내용`으로 자연스러웠으므로 Tool 호출 여부나 명백한 질의
오염 문제는 아니었다. 관련 없는 하위 청크까지 포함하는 topK 5와 4096 컨텍스트 안에서의 정보
선택 실패가 다음 핵심 가설이다.

따라서 이번 변경은 **출처 추적성과 답변 계약 개선**으로 범위를 한정한다. 사업 개요 정확도 문제는
다음 단계에서 topK와 컨텍스트 크기를 분리 비교해 해결한다.

## 2026-08-26 — 검색량 축소로 RAG distractor 억제

### 발견

검색 결과 구조화 후에도 “어떤 사업인지 핵심만 설명”이라는 질문을 로컬트랙 신청 자격으로
잘못 축소했다. Tool 호출 로그의 검색 질의는 `모두의 창업 프로젝트 사업 내용`으로 정상적이어서
질의 재작성보다 검색 결과 안의 정보 선택 문제를 의심했다.

### 진단

동일 질의를 bge-m3로 임베딩하고 pgVector 상위 5개를 직접 조회했다.

| 순위 | 유사도 | 내용 판정 |
|---:|---:|---|
| 1 | 0.653 | 트랙·선정 규모·토너먼트 구조 — 핵심 근거 |
| 2 | 0.622 | 사업 목적·지원 대상·트랙 구분 — 핵심 근거 |
| 3 | 0.569 | 신청 제한·재도전 우대 — 부분 관련 |
| 4 | 0.568 | 참여 제외·동시 수행 제한 — distractor |
| 5 | 0.560 | 중복 참여 불가 사업 목록 부록 — 강한 distractor |

검색기는 정답 청크를 1~2위에 올렸지만 topK 5가 하위 부록까지 생성 모델에 전달했다.
qwen3:8b는 상위 순위보다 구체적인 목록을 따라가며 질문 의도를 잃었다.

### 전략

8GB VRAM 환경에서 `num_ctx 8192`를 먼저 적용하면 KV cache 증가로 TTFT와 동시성이 악화될 수 있다.
따라서 한 번에 하나의 변수만 바꾸는 원칙으로 컨텍스트는 4096에 두고 topK만 5에서 3으로 줄였다.

운영 Tool과 실험 하네스가 다른 값을 사용하지 않도록 `RagSearchSettings`를 단일 기준점으로 추가했다.
Ollama 컨텍스트는 모델 기본값에 기대지 않고 4096으로 명시해 실행 환경의 재현성도 확보했다.

### 해결 및 검증

| 항목 | topK 5 | topK 3 |
|---|---:|---:|
| 검색 본문 문자 수 | 7,540자 | 4,616자 |
| 컨텍스트 감소 | 기준 | 38.8% 감소 |
| 사업 개요 적합성 | 실패 | 핵심 관련성 회복 |
| 출처 표시 | 성공 | 성공 |
| E2E 완료 시간 | 59.9초 | 76.0초 |

topK 3 답변은 다음 핵심을 포함했다.

- 전 국민 대상 창업 도전 사업
- 일반/기술트랙 8,000명, 로컬트랙 2,000명
- 창업활동자금·AI 솔루션·멘토링·GPU·MVP·사업화 지원
- 최대 5억원 상금과 공식 신청 홈페이지

완료 시간은 답변 생성량과 GPU 상태 영향을 받으므로 topK 축소의 속도 개선 근거로 사용하지 않는다.
대신 검색 본문 문자 수 38.8% 감소를 직접적인 컨텍스트 절감 수치로 사용한다.

### 남은 한계

답변은 “2R 진출 시 사업자등록 필수”를 두 트랙에 공통인 것처럼 표현했다. 원문은
일반/기술트랙 3R, 로컬트랙 2R로 서로 다르다. 핵심 관련성은 회복했지만 세부 조건의 트랙 귀속에는
오류가 남아 있어 완전 성공으로 평가하지 않는다.

단일 질문에 계속 맞추면 과적합될 수 있으므로 추가 프롬프트 수정은 중단한다. 다음 단계에서 실제
PDF 기반 다문항 생성 품질 평가셋을 먼저 만들고, 트랙별 조건·수치 귀속 오류를 재현 가능한 지표로
측정한 뒤 개선한다.

## 2026-08-26 — PDF 기반 RAG 생성 품질 평가셋 구축

### 발견

기존 RAG 실험은 검색 Recall만 측정했다. 실제 PDF 테스트에서는 정답 청크가 검색돼도 모델이
핵심을 누락하거나 트랙별 조건을 잘못 연결했으므로, 검색 지표만으로 최종 사용자 답변 품질을
보장할 수 없었다.

### 평가 설계

34페이지 정부 공고문에서 사용자가 실제로 물을 만한 8개 범주를 선정했다.

- 사업 개요, 트랙 차이
- 일반/기술 및 로컬 라운드별 인원
- 트랙별 사업자등록 시점과 최대 상금
- 예비·기창업자 신청 자격
- 신청 기간·마감 시각·사이트

각 문항은 정규식 기반 필수 사실과 금지 오답을 가지며, 통과 조건을 다음처럼 엄격하게 정의했다.

1. 필수 사실 100% 포함
2. 금지 오답 0건
3. `[출처]` 표시

실제 `ChatClient + Tool Calling + pgVector + qwen3:8b` 전체 경로를 순차 실행하고, 필수 사실 포함률,
문항 통과율, 출처 표시율, 평균·p95 응답 시간을 자동 보고서로 생성한다. 일반 테스트에서는
외부 의존 실험을 제외하고 `ragGenerationQualityExperiment` 태스크로만 실행하게 분리했다.

### 평가 도구 자체에서 발견한 문제

#### 1. 사용하지 않는 외부 provider가 실험 기동을 차단

첫 실행은 문항 처리 전에 Anthropic API 키가 없어 ApplicationContext가 실패했다. 팩토리 내부에서
예외를 흡수해도 자동설정 빈의 선생성까지 막지는 못했다. Ollama 전용 실험 태스크에 외부 통신을
하지 않는 더미 키를 주입해 멀티 provider 빈 생성 조건만 충족하도록 수정했다.

#### 2. 8분 실행 후 보고서 포맷 오류

두 번째 실행은 8문항을 모두 생성했지만 마지막 보고서의 p95 `long` 값을 `%.1f`로 포맷해
`IllegalFormatConversionException`이 발생했다. Gradle XML에서 판정과 지연은 복구했지만 상세 답변은
인메모리 ChatMemory와 함께 사라졌다.

- 원인: `p95LatencyMs / 1000`이 정수형인데 부동소수점 포맷 사용
- 수정: `p95LatencyMs / 1000.0`으로 변환
- 재발 방지: 문항 하나가 끝날 때마다 보고서를 증분 저장

평가 대상 코드뿐 아니라 **평가 하네스 자체도 실패 복구 가능하게 설계해야 한다**는 교훈을 얻었다.

### 최종 실행 결과

실행 시간 8분 25초, 8문항 순차 평가 기준이다.

| 지표 | 자동 엄격 기준 |
|---|---:|
| 문항 통과율 | 12.5% (1/8) |
| 필수 사실 포함률 | 28.6% (6/21) |
| 출처 표시율 | 100% (8/8) |
| 평균 응답시간 | 60.4초 |
| p95 응답시간 | 87.1초 |

상세 사람 검토에서 `track-1`과 `eligibility-1`은 의미상 정답이지만 표현이 정규식과 달라
실패 처리된 것을 확인했다. 사람 검토 보정 기준은 문항 통과율 37.5%(3/8), 필수 사실 포함률
38.1%(8/21)다. 자동 지표는 반복 비교용 엄격 기준으로 그대로 보존한다.

### 반복 실행에서 확인한 변동성

보고서 오류가 난 직전 실행의 복구 가능 지표와 최종 실행을 비교했다.

| 항목 | 직전 실행 | 최종 실행 |
|---|---:|---:|
| 자동 통과 | 2/8 | 1/8 |
| 필수 사실 | 11/21 | 6/21 |
| 출처 표시 | 8/8 | 8/8 |
| 평균 지연 | 61.9초 | 60.4초 |
| p95 지연 | 100.4초 | 87.1초 |

동일 설정에서도 일반/기술 라운드와 로컬 라운드의 통과 결과가 서로 뒤바뀌었다. 반면 사업자등록은
두 번 모두 1/3, 상금은 0/2, 신청 정보는 0/4로 실패해 안정적으로 취약한 영역이 드러났다.

### 결론과 다음 개선 후보

- 출처 계약은 2회 총 16답변에서 100% 유지돼 안정적이다.
- 작은 모델의 Tool 검색 질의와 사실 선택은 비결정적이며 단발성 성공으로 품질을 주장할 수 없다.
- topK를 줄여 개요 질문의 distractor는 완화했지만, 세부 수치 질문은 threshold 0.5에서 검색 적중이
  1~2건으로 줄거나 필요한 표 정보를 놓친다.
- 다음 RAG 개선은 전역 topK 재조정보다 질문 유형별 검색 전략, 표 구조 보존, 반복 평가를 기준으로
  해야 한다.

## 2026-08-26 — 로컬 모델 대기 UX와 스트리밍 Markdown 개선

### 문제와 근거

PDF 생성 품질 평가에서 qwen3:8b의 평균 응답 시간은 60.4초, p95는 87.1초였다. 기존 화면은
요청 직후 빈 `TOKEN`을 연결 신호로 재사용해 “서버가 요청을 받았는지”, “첫 토큰을 기다리는지”,
“답변을 생성 중인지”를 구분하지 못했다. 사용자는 긴 정상 처리도 멈춤이나 전송 실패로 오해할 수 있었다.

답변 영역도 기본 Markdown 스타일에만 의존해 표의 가로 스크롤, 코드 언어 표시·복사, 긴 문단의
여백이 부족했다. 포트폴리오 데모에서는 모델 성능뿐 아니라 기다리는 과정과 결과를 읽는 경험도
완성도의 일부라고 판단했다.

### 프로토콜과 화면 개선

- 연결 확인 `READY`, 요청 접수 `QUEUED`, 내용 스트림 `TOKEN`을 분리했다.
- `QUEUED` 수신 즉시 서버 접수 문구, 경과 시간, 10초 이후 로컬 모델 지연 안내를 표시했다.
- 첫 내용 토큰부터는 입력창 문구를 `답변 생성 중...`으로 바꿔 처리 단계를 구분했다.
- 답변 전용 `MarkdownMessage`를 추출해 제목·문단·목록·인용문 여백을 정리했다.
- 표는 테두리와 가로 스크롤을 적용하고, 코드 블록에는 언어명과 복사 피드백을 추가했다.
- 시스템 프롬프트에 Markdown 블록·표 행·코드 블록의 실제 개행 규칙을 명시했다.

### 브라우저 E2E에서 발견한 숨은 원인

첫 실시간 테스트에서는 제목, 목록, 표가 한 줄로 붙었지만 같은 답변을 새로고침하면 정상적으로
렌더링됐다. 이 차이로 모델 원문이나 CSS보다 **실시간 전송 경로와 저장 경로의 불일치**를 의심했다.

`TokenTrackingAdvisor`는 모든 청크를 저장하는 반면 WebSocket 핸들러는 `text.isBlank()`인 청크를
버리고 있었다. Ollama가 Markdown 줄바꿈을 독립적인 공백 청크로 보내면 실시간 화면에서만 개행이
사라지는 구조였다. 필터를 `isEmpty()`로 좁혀 내용이 없는 청크만 제외하고 줄바꿈은 보존했다.

### 검증

격리된 로컬 QA 계정에서 제목, 목록, 표, JavaScript 코드 블록을 요구하는 실제 qwen3:8b 요청을
두 차례 실행했다.

| 검증 항목 | 결과 |
|---|---|
| 요청 접수 상태 | 전송 약 1.5초 후 `QUEUED` 문구와 경과 시간 확인 |
| 최종 응답 | 약 25.2초 후 제목·목록·표·코드 블록이 스트리밍 화면에서 정상 분리 |
| 저장 이력 | 새로고침 후에도 동일한 Markdown 구조 유지 |
| 코드 복사 | 클릭 후 `복사됨` 피드백 확인 |
| 백엔드 테스트 | 29건 통과, 실패·오류 0건 |
| 프론트엔드 정적 검증 | ESLint 및 TypeScript/Vite 프로덕션 빌드 통과 |

이번 문제는 “Markdown CSS 보강”만으로는 해결되지 않았다. 스트리밍 중 화면과 저장 후 화면을
비교한 것이 공백 청크 손실을 발견하는 결정적 단서였고, 프로토콜 수준에서 수정해 모든 Markdown
렌더러가 동일한 원문을 받도록 만들었다.

## 2026-08-26 — 로컬 모델 대화 품질 기준선 구축

### 문제

PDF RAG 평가는 문서 사실 정확도만 측정한다. 실제 사용자 테스트에서 나타난 서비스 정체성 오류,
이전 대화 기억, 문서 대화 이후의 주제 전환, Markdown 출력 계약은 기존 지표로 재현할 수 없었다.
생성 파라미터나 모델을 바꿔도 같은 질문으로 비교하지 않으면 개선 여부를 판단할 근거가 없었다.

### 평가 설계

다음 네 시나리오를 JSON 평가셋과 정규식 판정기로 구성했다.

- 서비스가 자신을 BTLLM으로 소개하고 모델 제작사를 사칭하지 않는가
- 같은 대화 안에서 사용자가 지정한 코드명을 기억하는가
- 창업 지원 배경을 들은 뒤 자격 설명을 반복하지 않고 1인 개발 아이디어로 전환하는가
- 정확히 요구한 Markdown 표·사용자·수익 모델 계약을 따르는가

모델, temperature, top-p, top-k, Thinking, 컨텍스트, 최대 출력 토큰, 반복 횟수를 환경변수로
주입할 수 있게 해 이후 실험이 같은 코드와 평가셋을 사용하도록 했다. 실제 Ollama를 호출하는 태스크는
별도 태그로 격리해 일반 테스트와 CI에서는 실행하지 않는다. 장시간 실행이 중단돼도 완료된 문항을
잃지 않도록 문항마다 보고서를 갱신한다.

### 현재 Qwen3 8B 기준선

설정은 `temperature=0.3`, `top_p=0.8`, `top_k=20`, Thinking 비활성, `num_ctx=4096`이다.

| 지표 | 결과 |
|---|---:|
| 자동 시나리오 통과율 | 0.0% (0/4) |
| 요구사항 충족률 | 88.9% (8/9) |
| 평균 지연 | 4.6초 |
| p95 지연 | 11.2초 |

### 발견

0%라는 결과만 보면 모델 이해력이 전부 실패한 것처럼 보이지만 상세 응답은 다른 원인을 보여줬다.

- 단기 기억은 `보라돌이`를 정확히 회상했다.
- 주제 전환 후에는 자격요건을 반복하지 않고 1인·8주·MVP 조건의 아이디어 3개를 제시했다.
- Markdown 표와 대상 사용자·수익 모델도 모두 충족했다.
- 그러나 모든 일반 답변에 `[출처]` 또는 `[출처] 사용자 제공 정보`를 붙였다.
- 정체성 질문에는 일반 AI 어시스턴트라고 답했지만 BTLLM이라는 서비스 이름은 알지 못했다.

즉 이번 기준선은 **작은 모델의 이해 실패와 시스템 프롬프트 정책 오류를 분리**했다. 현재 가장 큰
공통 실패 원인은 모델 체급보다 “사용한 문서 파일명을 항상 출처로 표시”한다는 조건이 비-RAG 답변까지
일반화된 것이다. 다음 단계에서는 출처 계약과 서비스 정체성을 먼저 바로잡은 뒤 동일 평가를 반복하고,
그 후 생성 파라미터와 Qwen3.5 모델을 비교한다.

## 2026-08-27 — 로컬 모델 품질/성능 개선 사전 리서치

### 왜 리서치부터 했는가

이전 기준선에서 원인은 밝혔지만(“출처 규칙 일반화”), 수정 방법은 여러 갈래(프롬프트만 고칠지,
검색 구조를 바꿀지, 모델을 바꿀지)였다. 파라미터·모델 교체부터 시행착오로 시작하면 근거 없는
변경이 되므로, 먼저 “8GB급 GPU에서 로컬 LLM을 실사용 가능한 수준으로 끌어올리는 방법”을
웹에서 조사해 우리 상황(qwen3:8b, RTX 4060 Ti 8GB, bge-m3, topK 3)에 맞는 것만 추렸다.

### 조사 결과 요약

- **2단계 검색(retrieve→rerank)**: 벡터 검색으로 넓게(k=10~30) 가져온 뒤 cross-encoder
  reranker(`bge-reranker-v2-m3` 등)로 재정렬해 상위 몇 개만 LLM에 전달하는 구조가
  업계 표준으로 자리잡음. 우리가 겪은 “정답 청크가 검색 순위 1~2위인데 생성이 무시” 현상의
  유력한 해결책 후보로 판단.
- **완전 GPU 오프로드 필수**: 8GB VRAM에서 부분 오프로드 시 실측 4.7배 속도 저하 사례 확인.
  우리가 겪은 VRAM 포화 시 0.86 t/s 현상과 동일 메커니즘.
- **KV 캐시 비용**: 컨텍스트를 4K→32K로 늘리면 1~2GB 추가 소요 — `num_ctx` 상향 전에
  VRAM 예산을 계산해야 함을 확인.
- **Qwen3.5-9B**가 8GB 티어 벤치마크에서 우위이나 Ollama 지원이 아직 불안정하다는 경고 존재 —
  교체보다 `qwen3.5:4b-q8_0` 같은 저위험 대안을 먼저 검토하기로 함.
- **작은 모델의 tool calling/지시 준수는 파인튜닝 없이 프롬프트 어조·few-shot 예시만으로도
  개선 가능**하다는 연구 결과 확인. 이는 이전 세션에서 이미 경험적으로 발견한
  “도구 설명 어조를 단정형으로 바꾸니 호출률이 0→100%” 사례와 정확히 일치해, 이번 출처 문제도
  같은 접근(지시문 강화 + few-shot)으로 먼저 시도해보기로 결정.

## 2026-08-27 — 서비스 정체성·조건부 출처 계약 수정 (1차)

### 조치

리서치에서 검증된 접근대로 프롬프트만 먼저 고쳤다. `ChatClientFactory.SYSTEM_PROMPT`에 두 가지를 추가했다.

1. 서비스 정체성: "너는 BTLLM이다. Qwen/알리바바를 사칭하지 마라."
2. 조건부 출처: "`searchKnowledgeBase`를 실제로 호출했을 때만 `[출처]`를 붙여라. 일반 대화·방금 사용자가
   준 정보에는 절대 붙이지 마라."

### 1차 검증 (3회 반복)

| 지표 | 이전 기준선 | 1차 수정 후 |
|---|---:|---:|
| 시나리오 통과율 | 0.0% (0/4) | 41.7% (5/12) |
| 요구사항 충족률 | 88.9% (8/9) | 85.2% (23/27) |

- `format-1`은 3/3 유지.
- `context-shift-1`은 0/1 → 2/3로 개선(1회는 여전히 `[출처]` 누출).
- `identity-1`은 여전히 0/3 — 원인은 정책 문제가 아니라 **평가 기준과 응답의 불일치**였다.
  골든셋은 `["BTLLM"]`과 `["AI", "인공지능", "어시스턴트"]` 두 그룹을 모두 요구하는데,
  모델은 "저는 BTLLM입니다"만 답하고 "AI"라는 단어 자체를 쓰지 않았다.
- `memory-1`은 2/3에서 `[출처]`가 여전히 붙었다 — 코드명을 정확히 기억하면서도 관성적으로
  출처 표기를 반복.

### 2차 조정과 재검증

1. identity: 시스템 프롬프트에 "BTLLM"과 "AI 어시스턴트" 두 표현을 모두 답변에 넣으라고 예시까지 명시.
2. 출처: 좋은 예시/나쁜 예시(few-shot)를 추가하고 "답변 전에 이번 턴에 도구를 호출했는지 스스로
   확인하라"는 자기 점검 지시를 추가.

| 지표 | 1차 수정 후 | 2차 조정 후 |
|---|---:|---:|
| identity-1 통과 | 0/3 | **3/3** |
| memory-1 통과 | 1/3 | 0/3 |
| context-shift-1 통과 | 2/3 | 0/3 |

identity는 few-shot 예시로 완전히 해결됐다. 그런데 memory·context-shift는 오히려 나빠졌다 —
단, 원인이 서로 다르다.

- `memory-1`: `[출처]` 누출은 3/3 모두 사라졌다(수정 성공). 대신 모델이 "보라돌이"를 "보라돌"로
  한 글자 빠뜨려 정규식 매칭에 실패했다 — 이는 출처 규칙과 무관한 별개의 소형 모델 오타 이슈.
- `context-shift-1`: 여전히 `[출처]`가 3/3 모두 붙는다. 원인을 골든셋 setup을 보고 특정했다 —
  이 시나리오는 setup 프롬프트로 "모두의 창업 프로젝트는 …" 라는 **문서 내용과 흡사한 배경 지식**을
  대화에 먼저 심어준다. 실제 `searchKnowledgeBase` 호출은 없었는데도, 모델이 대화 맥락만 보고
  "이건 문서 얘기니까 출처를 붙여야 한다"고 패턴 매칭하는 것으로 보인다.

### 잠정 결론

**프롬프트 지시 + few-shot만으로는 조건부 출처 규칙의 신뢰도에 한계가 있다.** 도구를 실제로
호출했는지와 무관하게, 대화 주제가 "문서스러우면" 모델이 출처 표기 패턴을 재현한다. 이는 사전
리서치에서 확인한 "프롬프트만으로 작은 모델의 지시 준수를 끌어올리는 데는 한계가 있고,
결정론적 가드레일을 병행해야 한다"는 내용과 일치하는 실측 사례다.

**다음 단계 후보(결정 대기)**: 프롬프트 수정만으로는 한계에 도달했으므로, 이번 턴에 실제
`searchKnowledgeBase` tool call이 있었는지를 코드에서 추적해 없으면 `[출처]` 문자열을
후처리로 강제 제거하는 결정론적 가드레일 도입을 검토한다.

### 결정

`[출처]` 오적용은 실사용 체감 임팩트가 낮은 흠(문서와 무관한 일반 대화에 태그 하나 더 붙는 수준)으로
판단해 **코드 레벨 가드레일 도입은 백로그로 미룬다.** 대신 리서치에서 더 근본적인 개선으로 짚었던
"검색 결과 reranking" 실험으로 먼저 넘어간다 — RAG 생성 실패(정답 청크를 받고도 무시)가
사용자 체감 품질에 더 크게 영향을 준다고 판단했기 때문이다.

## 2026-08-27 — 하이브리드 재정렬(벡터+키워드) 도입과 한계 확인

### 설계 결정: cross-encoder 대신 순수 계산 재정렬

리서치에서 확인한 대로 Ollama는 `/api/rerank`를 지원하지 않는다. `bge-reranker-v2-m3` 같은
cross-encoder를 쓰려면 `llama.cpp`의 `llama-server --reranking`을 별도 프로세스로 띄워야 하는데,
이미 RTX 4060 Ti 8GB에서 qwen3:8b(5.6GB)+bge-m3(0.7GB)로 VRAM이 빠듯한 상태에서 GPU 모델을
하나 더 얹으면 VRAM 포화 시 0.86 t/s까지 떨어지는 기존 문제를 재현할 위험이 컸다. CPU 서빙도
가능하지만, 먼저 **새 인프라 없이** 순수 Java 계산(벡터 유사도 0.7 + 키워드 겹침 0.3 가중합)으로
효과가 있는지 싸게 검증하기로 했다.

### 구현

- `HybridReranker`(`rag/service/HybridReranker.java`): 공백/구두점 기준 토큰화 후
  질의 토큰이 문서 텍스트에 포함된 비율을 키워드 점수로 계산, `Document.getScore()`(벡터 유사도)와
  가중합해 재정렬.
- `LlmTools.searchKnowledgeBase`: 벡터 검색을 `TOP_K`(3)가 아니라 `RERANK_CANDIDATE_K`(10)로
  넓게 가져온 뒤 재정렬해서 최종 3개만 프롬프트에 전달하도록 변경.
- 유닛 테스트 3건(`HybridRerankerTest`)으로 재정렬 로직만 격리 검증, 기존 `LlmToolsTest`는
  새 의존성을 실제 인스턴스로 주입하도록 수정.

### 검증 — 실제 PDF 골든셋 8문항

| 지표 | 이전(리랭커 도입 전) | 이후 |
|---|---:|---:|
| 문항 통과율 | 12.5% (1/8) | **25.0% (2/8)** |
| 필수 사실 포함률 | 28.6% (6/21) | 28.6% (6/21) — 동일 |
| 출처 표시율 | 100% (8/8) | 100% (8/8) |
| 평균 응답시간 | 60.4s | **29.0s** |
| p95 응답시간 | 87.1s | **35.5s** |

통과율은 개선됐고 지연도 크게 줄었다(다만 지연 개선은 이번 세션의 다른 변경—시스템 프롬프트,
GPU 여유 상태 차이—과 섞여 있어 재정렬만의 효과로 단정하지 않는다. 별도로 분리 측정하지 않았다는
점을 한계로 남긴다).

### 남은 한계 — 재정렬로 못 고치는 실패 유형을 특정함

가장 중요했던 사례인 `overview-1`("이 사업 핵심만 설명해줘")은 **여전히 실패**했다. 로그를 보면
원인이 명확하다.

```
지식베이스 검색 — query: 모두의 창업 프로젝트, 후보: 8건, 최종: 3건
```

모델이 만든 검색 질의 자체가 "모두의 창업 프로젝트"처럼 짧고 일반적이었다. 이런 질의는 문서 제목이
반복 등장하는 신청자격·신청방법 조항과의 임베딩 유사도가 높게 나와, **애초에 후보 풀(8건)에
사업개요 청크가 들어오지 않았다.** 재정렬은 이미 검색된 후보의 순서만 바꿀 뿐 후보 자체를 늘리지
못하므로 이 실패 유형(Recall 실패)에는 구조적으로 무력하다. `track-1`, `round-local-1`도
같은 패턴(후보 2~3건으로 이미 좁음)으로 실패했다.

**결론**: 이번 실험으로 RAG 실패를 두 갈래로 명확히 분리했다.
1. **랭킹 실패**(정답이 후보 안에 있지만 순위가 밀림) — 하이브리드 재정렬로 부분 완화 확인
2. **Recall 실패**(정답이 애초에 후보에 없음, 질의가 너무 짧거나 일반적) — 재정렬로는 해결 불가,
   질의 확장(query expansion)이나 후보 풀 확대, 청크 단위 재설계가 필요

다음 단계 후보(결정 대기): overview류 질문의 Recall 실패를 해결하려면 (a) `searchKnowledgeBase`
설명에 질의를 더 구체적으로 만들라는 지침 추가, (b) 문서 요약 청크를 별도로 인덱싱해 항상 후보에
포함, (c) 유사도 임계값을 낮춰 후보 폭을 넓히는 방법을 비교해야 한다.

## 2026-08-27 — OpenAI provider 연동과 `.env` 기반 키 주입

### 배경

로컬 모델의 실패가 파이프라인 탓인지 모델 체급 탓인지 가르려면 **같은 파이프라인에 모델만 바꿔
끼울 수 있어야** 한다. 기존 provider 확장 지점(claude/gemini)이 이미 있었으므로 OpenAI를 같은
패턴으로 추가했다.

### 구현

`build.gradle`에 `spring-ai-starter-model-openai`를 추가하고, `ChatClientFactory`에
`ObjectProvider<OpenAiChatModel>` 기반 조건부 로딩·라우팅을, `ModelController`에 목록 노출을
더했다. 프론트엔드는 `/api/v1/models` 응답으로 렌더링하므로 provider 배지 이모지 외에는 변경이
없었다.

### 트러블슈팅 ① — EmbeddingModel 빈 중복으로 기동 실패

OpenAI 스타터를 추가하자마자 앱이 죽었다.

```
No qualifying bean of type 'EmbeddingModel' available:
expected single matching bean but found 2: ollamaEmbeddingModel, openAiEmbeddingModel
```

- **진단**: 두 스타터의 임베딩 오토컨피그를 디컴파일해 확인하니 양쪽 모두
  `@ConditionalOnProperty(name="spring.ai.model.embedding", matchIfMissing=true)`였다.
  즉 속성을 명시하지 않으면 **둘 다 활성화**되는 구조였고, 그동안은 Ollama 하나뿐이라
  문제가 드러나지 않았을 뿐이다.
- **개선**: RAG 임베딩은 한국어 성능 때문에 bge-m3로 고정해야 하므로
  `spring.ai.model.embedding: ollama`를 명시했다.
- **교훈**: `matchIfMissing=true` 오토컨피그는 provider가 하나일 때는 편의지만, 둘째가
  들어오는 순간 충돌한다. 멀티 provider 구성에서는 기본값에 기대지 말고 명시해야 한다.

### 트러블슈팅 ② — 쓰지도 않는 TTS 오토컨피그가 기동을 막음

임베딩을 고정한 뒤에도 `openAiAudioSpeechModel` 생성 실패로 죽었다. OpenAI 스타터는 Chat 외에
Audio Speech·Transcription·Image·Moderation 오토컨피그를 함께 들여오는데, 이들은 우리
`ChatClientFactory`처럼 `ObjectProvider` + try-catch로 감싸져 있지 않아 키가 없으면 컨텍스트
초기화 자체를 중단시킨다. 쓰지 않는 4개를 `spring.autoconfigure.exclude`로 제외했다.

### 트러블슈팅 ③ — `.env`를 만들었는데 키가 주입되지 않음

`spring.config.import: optional:file:.env[.properties]`로 `.env`를 읽게 한 뒤에도
`SPRING_AI_OPENAI_API_KEY`가 인식되지 않았다.

- **진단**: Spring의 대문자·언더스코어 완화 바인딩(`SPRING_AI_OPENAI_API_KEY` →
  `spring.ai.openai.api-key`)은 **OS 환경변수에만** 적용되고, properties 파일의 키 이름에는
  적용되지 않는다. `.env`의 그 줄은 그냥 이름이 특이한 무관한 속성으로 읽히고 있었다.
- **개선**: yaml에 `api-key: ${SPRING_AI_OPENAI_API_KEY:}` 플레이스홀더를 명시해 파일·환경변수
  양쪽에서 주입되게 했다. Anthropic도 같은 이유로 동일 처리했다.
- **검증**: 셸 환경변수를 전혀 주지 않고 `.env`만으로 `bootRun` → `Started BtllmApplication` 확인.
- **교훈**: "설정 파일을 읽는 데 성공한 것"과 "값이 목적지 속성에 바인딩된 것"은 다른 문제다.
  기동 성공만 보고 넘어갔다면 키가 비어 있는 채로 실험을 돌릴 뻔했다.

### 남은 한계

Google provider는 키가 비어 있으면 `CachedContentService`가 우리 예외 흡수 범위 밖에서 실패해
기동을 막는다. 현재는 임의 더미 값으로 우회하며 README에 명시했다. 근본 수정(조건부 exclude)은
백로그.

## 2026-08-27 — 동일 골든셋 Provider 비교로 실패 원인 분리

### 문제

지금까지 로컬 qwen3:8b만 측정해왔기 때문에, RAG 실패를 볼 때마다 **"검색이 근거를 못 준 것"과
"모델이 근거를 받고도 못 쓴 것"을 구분할 수 없었다.** 이 구분 없이는 다음 개선을 검색 쪽에
투자할지 모델 쪽에 투자할지 결정할 근거가 없다.

### 실험 설계 — 상용 API를 대체재가 아니라 '기준선'으로 사용

`ProviderComparisonExperiment`를 추가해 **동일 골든셋·동일 검색 파이프라인·동일 시스템 프롬프트에
모델만 교체**해 실행한다. 통제 항목은 다음과 같다.

- 같은 골든셋 파일(`/rag-eval/generation-golden-set.json`)과 같은 판정기(`RagAnswerEvaluator`)
- 같은 `LlmTools`(searchKnowledgeBase + HybridReranker), 같은 topK·후보 수·임계값
- 같은 시스템 프롬프트(`ChatClientFactory`가 provider 무관하게 적용)

대상은 `PROVIDER_COMPARISON_TARGETS=provider=model,...` 환경변수로 바꾼다(모델명에 콜론이 있어
구분자로 `=`를 썼다). 키가 없는 provider는 자동으로 건너뛰고 보고서에 사유를 남긴다.
상용 API는 실제 과금이 발생하므로 일반 `test`에서 태그로 완전히 제외했다.

### 결과 — qwen3:8b vs gpt-4o-mini (동일 8문항)

| Provider / 모델 | 문항 통과율 | 필수 사실 포함률 | 출처 표시율 | 평균 지연 | p95 지연 |
|---|---:|---:|---:|---:|---:|
| ollama / qwen3:8b | 25.0% (2/8) | 33.3% (7/21) | 100% (8/8) | 47.9s | 64.9s |
| openai / gpt-4o-mini | 62.5% (5/8) | 76.2% (16/21) | 100% (8/8) | **6.0s** | **11.9s** |

문항별 비교에서 **원인이 세 갈래로 갈렸다.**

| 문항 | qwen3:8b | gpt-4o-mini | 해석 |
|---|---:|---:|---|
| eligibility-1, round-local-1 | ✅ | ✅ | 검색·생성 모두 정상 |
| track-1, round-general-1, application-1 | ❌ | ✅ | **모델 체급 문제** — 같은 근거로 GPT는 성공 |
| prize-1, registration-1 | ❌ | ❌ | **검색 문제** — 근거 자체가 부족 |
| overview-1 | ❌ 1/4 | ❌ 3/4 | 검색 부족 + 체급이 겹침 |

특히 `application-1`(신청 방법)은 로컬이 0/4, GPT가 4/4였다. 검색 결과는 동일했으므로 이 실패는
검색이 아니라 **소형 모델이 받은 근거에서 필요한 사실을 뽑아내지 못한 것**이다. 반대로 `prize-1`은
GPT도 0/2라 모델을 아무리 키워도 해결되지 않는다 — 상금 정보가 애초에 후보 청크에 없다는 뜻이다.

### 이 실험의 의미

단일 모델만 측정할 때는 모든 실패가 뭉뚱그려져 "RAG 품질이 낮다"로만 보였다. 모델을 교체 가능한
변수로 만들자 **같은 지표가 검색 개선 과제와 모델 선택 과제로 분해**됐다. 앞으로 검색 쪽 개선
(질의 확장, 요약 청크 인덱싱)은 `prize-1`·`registration-1`·`overview-1`로, 모델 쪽 개선
(파라미터 튜닝, Qwen3.5 교체)은 `track-1`·`round-general-1`·`application-1`로 효과를 판정한다.

지연 격차(47.9s vs 6.0s)도 확인했다. 로컬 모델의 가치는 속도나 정확도가 아니라 **비용과
프라이버시**에 있으며, 8GB VRAM 환경에서 상용 API 수준의 응답성을 기대할 수 없다는 점을
수치로 확정했다.

### 남은 한계

- 각 provider 1회 실행이라 분산을 보지 못했다. 로컬 모델은 앞선 실험에서 실행 간 편차가
  관측됐으므로(같은 8문항에서 통과율 12.5%~25.0%), 결론을 굳히려면 반복 실행이 필요하다.
- 지연 비교는 네트워크 왕복과 로컬 GPU 상태가 뒤섞인 값이다. 공정한 비교라기보다 사용자 체감의
  근사치로만 해석한다.

## 2026-08-27 — 요약 청크 가설 검증 실패와 컨텍스트 초과 발견

### 가설과 구현

`overview-1`의 Recall 실패를 풀기 위해 색인 시점에 문서 전체 개요를 요약한 청크를 추가로
생성하는 `DocumentSummarizer`를 만들었다. 문서당 LLM 1회 호출이며(청크당 호출로 제거됐던
KeywordMetadataEnricher의 전례를 피함), 요약 실패가 본문 색인을 막지 않도록 예외를 흡수한다.

### 측정 도중 발견한 통제 문제

재색인 결과 코퍼스가 **21청크·31,096자 → 38청크·206,147자**로 달라졌다. 데스크톱의 원본 PDF가
이전 색인본보다 훨씬 컸다. 기존 25% 기준선과 비교하면 무효이므로, **같은 38청크 코퍼스에서
기준선을 다시 측정**한 뒤 요약 청크만 추가하는 A/B로 통제했다.

| | 기준선(38청크) | 요약 청크 추가 |
|---|---:|---:|
| 문항 통과율 | 0.0% (0/8) | 0.0% (0/8) |
| 필수 사실 포함률 | 38.1% (8/21) | 33.3% (7/21) |
| 평균 응답시간 | 65.8s | 72.1s |

### 원인 규명 — 검색 단계 직접 진단

최종 답변만으로는 "요약 청크가 검색되지 않은 것"과 "검색됐는데 모델이 못 쓴 것"을 구분할 수 없어
`SummaryChunkRetrievalDiagnostic`을 만들어 검색 단계만 관측했다. 결과:

- 요약 청크는 개요형 질의에서 **1위**, 짧은 질의에서 3위로 정상 검색된다. 검색 전제는 맞았다.
- 그러나 본문의 `1 사업 개요` 청크도 이미 **1~2위**로 검색되고 있었다. 현재 코퍼스에서는
  **애초에 Recall 실패가 아니었다.** 이전 진단은 21청크 시절 데이터에서 내린 것이었다.

### 그 과정에서 찾은 진짜 병목

| 항목 | 값 |
|---|---:|
| 본문 청크 평균 | 5,425자 (최대 10,117자) |
| 청크당 추정 토큰 | 약 1,507 |
| topK=3 근거 추정 토큰 | **약 4,521** |
| 설정된 `num_ctx` | **4,096** |

**검색된 근거만으로 컨텍스트 창을 초과한다.** 시스템 프롬프트·질문·도구 스키마는 계산 밖이다.
HANDOFF에 "잠재 폭탄"으로 적어뒀던 `num_ctx` 4096 문제가 코퍼스가 커지면서 실제로 터진 것이다.
`overview-1`이 선정 규모 수치(8,000명/2,000명)를 놓치는 것도 이것으로 설명된다.

### 결론

- 요약 청크는 현재 코퍼스에서 **중복**이다. 기능은 유지하되 기본 활성 여부는 컨텍스트 문제
  해결 후 재평가한다.
- **다음 최우선 과제는 컨텍스트 예산 관리**다. 청크 크기 축소 / `num_ctx` 상향(KV 캐시 증가와
  VRAM 트레이드오프) / 근거 길이 상한을 같은 골든셋으로 비교한다.

### 교훈

진단은 그것을 내린 시점의 데이터에만 유효하다. 낡은 진단 위에 기능을 얹었고, 중간 단계를
관측하지 않았다면 "넣었는데 왜 안 오르지"에서 멈췄을 것이다. **최종 지표가 움직이지 않을 때는
다음 가설보다 중간 단계의 관측 가능성을 먼저 확보해야 한다.**

### 부수 수정

- `DocumentSummarizer`가 `ChatClientFactory`의 클라이언트를 쓰자 `conversationId cannot be null`로
  실패했다. 팩토리 클라이언트에는 대화 이력 Advisor·도구·채팅 시스템 프롬프트가 붙어 있는데
  요약은 상태 없는 단발 변환이라 어느 것도 필요 없다. `OllamaChatModel`로 전용 클라이언트를
  따로 만들었다.
- 요약 헤더에 `%n`을 써서 Windows에서 `\r`이 색인 본문에 남았다. `\n`으로 고정했다.

## 2026-08-27 — 컨텍스트 예산 관리: 청크 크기 1500 → 800

### 가설

직전 진단에서 `topK=3` 근거가 약 4,521토큰으로 `num_ctx` 4,096을 초과함을 확인했다.
후보 세 가지(청크 축소 / `num_ctx` 상향 / 근거 길이 상한) 중 **청크 축소를 먼저** 골랐다.
`num_ctx` 상향은 KV 캐시 증가로 8GB VRAM을 압박할 위험이 있고, 청크 비대화가 이번 문제의
직접 원인이었기 때문이다.

### 구현

- 청크 크기를 `btllm.rag.chunk-size` 설정값으로 분리(기본 800). 색인 시점 파라미터라 변경 시
  재색인이 필요하고, 골든셋으로 크기별 비교를 하려면 코드 수정 없이 주입돼야 한다.
- **분할 직후 평균 청크 길이를 로그로 출력**하도록 추가했다. 이번 문제의 본질은 "설정한 토큰 수"와
  "실제 문자 수"의 관계가 언어·문서마다 다른데 그것을 볼 수단이 없었다는 점이다.

### 검증 — 동일 문서·동일 골든셋

| 지표 | 청크 1500 (38청크) | 청크 800 (63청크) |
|---|---:|---:|
| 문항 통과율 | 0.0% (0/8) | **50.0% (4/8)** |
| 필수 사실 포함률 | 38.1% (8/21) | **76.2% (16/21)** |
| 평균 응답시간 | 65.8s | **50.6s** |
| 청크 평균 길이 | 5,425자 | 3,225자 |
| topK=3 근거 추정 토큰 | 4,521 (초과) | 2,687 (여유) |

품질과 지연이 **동시에** 개선됐다. 컨텍스트가 짧아지면 프리필 연산이 줄어들기 때문이다.

### 원인 분해가 완벽하지 않았음을 보여준 결과

provider 비교(3-4)에서 gpt-4o-mini의 필수 사실 포함률이 76.2%였는데, 청크를 고친 로컬
qwen3:8b가 **같은 76.2%**를 기록했다. 그때 "모델 체급 문제"로 분류했던 실패 상당수가 사실은
컨텍스트 초과였다.

- `application-1`: 로컬 0/4 → **4/4**
- `prize-1`: 0/2 → **2/2** (GPT조차 실패해 "검색 문제"로 분류했던 문항)

provider 비교는 유효한 도구였지만, **두 모델이 동일하게 잘린 근거를 받고 있었다는 공통 조건**까지는
드러내지 못했다. 상용 모델은 잘린 근거로도 더 잘 버텼을 뿐이다. 통제 변수를 나눌 때, 두 조건에
공통으로 걸린 결함은 비교로 드러나지 않는다는 교훈.

### 남은 실패

`prize-1`은 필수 사실 2/2를 모두 포함했으나 금지 오답(일반/기술트랙 상금을 1억으로 서술)에 걸렸고,
`track-1`(0/2), `registration-1`(1/3), `overview-1`(3/4)이 남았다. 성격이 **여러 청크에 흩어진
사실을 트랙별로 올바르게 귀속시키는 문제**로 모인다. 컨텍스트에 여유가 생겼으므로 `topK` 상향,
`num_ctx` 8192, 표 구조 보존 청킹이 다음 후보다.

## 2026-08-27 — Provider 재비교: 로컬 모델이 상용 API와 동등 수준 도달

### 왜 다시 쟀는가

기존 provider 비교(로컬 25.0% vs GPT 62.5%)는 **청크 1500 시절 값**이다. 컨텍스트 초과를
고친 뒤에는 무효인데, 이 수치를 근거로 "로컬은 상용보다 한참 떨어진다"는 서술을 유지하면
잘못된 아키텍처 결론(품질이 필요하면 상용으로 라우팅)에 도달하게 된다. 그래서 재측정했다.

### 결과 — 동일 코퍼스(청크 800, 63청크)·동일 골든셋

| Provider / 모델 | 통과율 | 사실 포함률 | 평균 지연 | p95 |
|---|---:|---:|---:|---:|
| ollama / qwen3:8b | **62.5% (5/8)** | **81.0% (17/21)** | 45.3s | 78.3s |
| openai / gpt-4o-mini | 62.5% (5/8) | 76.2% (16/21) | 5.1s | 7.3s |

| | 청크 1500 시점 | 청크 800 시점 |
|---|---|---|
| 로컬 qwen3:8b | 25.0% / 33.3% | **62.5% / 81.0%** |
| gpt-4o-mini | 62.5% / 76.2% | 62.5% / 76.2% (변화 없음) |

**상용 모델 점수는 그대로인데 로컬만 올라 동률이 됐다.** 상용 모델은 잘린 근거로도 버티고
있었을 뿐이고, 근거를 온전히 주자 8B 로컬 모델이 같은 수준에 도달했다.

### 문항별 실패 패턴이 완전히 일치

성공 5문항(overview-1, round-general-1, round-local-1, eligibility-1, application-1)과
실패 3문항(track-1, registration-1, prize-1)이 두 모델에서 **정확히 겹친다.**

→ **남은 실패 3건은 모델 교체로 풀리지 않는다.** 파이프라인·데이터 표현 문제로 확정됐고,
앞으로 이 3문항으로 검색·청킹 개선의 효과만 판정하면 된다.

### 한계

각 provider 1회 실행이다. 로컬 모델은 동일 설정에서 실행 간 편차가 관측된 전력이 있어
(같은 8문항에서 0%~62.5%), 사실 포함률 81.0% vs 76.2%의 근소한 차이로 우위를 주장하지 않고
**"동등 수준 도달"까지만** 기록한다. 반복 실행은 남은 과제다.

### 교훈

**낡은 측정값을 근거로 아키텍처를 결정하면 안 된다.** 파이프라인을 고쳤으면 그 위에서 내렸던
모든 비교 판단을 다시 검증해야 한다. 이번엔 재측정 덕분에 "로컬은 품질이 부족하니 상용으로
라우팅한다"는 잘못된 결론을 피했다.

## 2026-08-27 — Provider 비교 3회 반복: 단발 결론을 스스로 반증

### 왜 반복했는가

직전 단발 비교에서 로컬 62.5% / 사실 81.0%, 상용 62.5% / 76.2%가 나와 "로컬이 상용과 동률,
사실 포함률은 오히려 우위"로 읽혔다. **내가 원하던 결론이었기 때문에 더 위험했다.**
로컬은 같은 골든셋에서 0%~62.5%로 흔들린 전력이 있어, 하네스에 반복 실행을 추가하고 3회씩 다시 쟀다.

### 결과 — 1차 결론은 부분적으로 틀렸다

| Provider / 모델 | 통과율 (24회) | 사실 포함률 | 평균 지연 | p95 |
|---|---:|---:|---:|---:|
| ollama / qwen3:8b | 50.0% (12/24) | **77.8% (49/63)** | 88.9s | **188.6s** |
| openai / gpt-4o-mini | **58.3% (14/24)** | **77.8% (49/63)** | 4.9s | 7.1s |

- 사실 포함률은 소수점까지 동일(77.8%) — **근거 활용도는 진짜 동등**하다.
- 통과율은 상용이 8.3%p 앞선다. 1차의 "동률"은 로컬이 좋은 회차를, 상용이 나쁜 회차를 뽑은
  우연이었다. 통과 조건이 *사실 100% + 금지 오답 0건*이므로 **같은 양의 사실을 뽑고도 로컬이
  오답을 더 자주 섞는다**는 의미다.

### 예상과 반대였던 것 — 편차는 로컬이 더 작았다

| Provider | #1 | #2 | #3 | 범위 |
|---|---:|---:|---:|---:|
| ollama / qwen3:8b | 50.0% | 50.0% | 50.0% | **0.0%p** |
| openai / gpt-4o-mini | 50.0% | 62.5% | 62.5% | 12.5%p |

반복을 도입한 명분이 "로컬이 불안정하니 확인하자"였는데 **로컬이 3회 모두 정확히 50.0%로
완전히 안정적**이었고 상용이 흔들렸다. 로컬의 과거 편차(0%~62.5%)는 모델의 비결정성이 아니라
**그 사이에 우리가 바꾼 파이프라인 설정 때문**이었다.

### 문항별 안정성 — 단발이 오도했던 지점

- `overview-1`: 1차에선 양쪽 ✅였으나 실제로는 **로컬 1/3회·상용 2/3회 간헐 통과**.
  단발만 봤다면 "해결됨"으로 분류하고 회귀 감시에서 뺐을 것이다.
- `round-local-1`: 로컬 2/3회 간헐.
- **`track-1`·`registration-1`·`prize-1`은 두 모델 모두 3회 전부 실패.** 총 12회 시도에서
  단 한 번도 통과하지 못해 **모델 교체로 풀리지 않음이 확정**됐다.
- `prize-1`은 **필수 사실 6/6을 모두 포함하고도 3회 전부 실패**했다. 금지 오답 패턴에 걸린
  것으로, 트랙별 수치 교차 귀속 문제이거나 골든셋 판정 기준 재검토가 필요한 사례다.

### 교훈

1. **단발 결과는 유리한 방향으로도 오도한다.** 원하던 결론일수록 반복 측정으로 걸러야 한다.
2. **가정은 반대 방향으로도 틀린다.** "로컬이 불안정할 것"이라는 전제가 틀렸고,
   과거 편차의 진짜 원인은 우리 설정 변경이었다.
3. 이제 로컬 대 상용은 우열이 아니라 **트레이드오프**로 서술할 수 있다:
   근거 활용도 동등 / 오답 안정성은 상용 / 속도는 상용 압도 / 비용·프라이버시는 로컬.

## 2026-08-27 — 로컬 지연 진단: 두 번 틀리고 세 번째에 원인을 찾다

### 문제

3회 반복 측정에서 로컬 응답이 평균 88.9초, p95 188.6초였다. 품질 격차는 좁혔지만 지연이
실사용을 막는 수준이었다(상용 p95 7.1초).

### 1차 가설 — 출력이 길다 (실패)

`chat_histories`의 토큰 기록에서 완성 토큰 평균 865(최대 1,985)를 보고 `num_predict`를 512로 제한했다.

| 지표 | 기준선 | num_predict 512 |
|---|---:|---:|
| 평균 지연 | 88.9s | 80.5s |
| 필수 사실 포함률 | 77.8% | 81.0% |
| **출처 표시율** | 100% | **37.5%** |
| 문항 통과율 | 50.0% | 25.0% |

`[출처]`는 답변 마지막 줄이라 절단되면 출력 계약이 먼저 깨진다. 필수 사실은 앞부분에 나와
포함률은 오히려 올랐다. **정확도가 아니라 계약 준수를 파괴하면서 지연 개선은 8.4초뿐**이라 되돌렸다.

**진단 데이터 자체가 틀렸다는 것도 이때 드러났다.** 그 토큰 기록은 실험 실행분이 아니라 이전
수동 세션의 것이었다. 실험은 임시 conversationId를 쓰므로 `chat_histories`에 남지 않는다.
*측정 도구가 무엇을 측정하고 있는지부터 확인해야 한다.*

### 2차 가설 — VRAM 압박 (실패)

VRAM 93%(7,658/8,188 MiB) 상태에서 생성 속도가 36.1 tok/s로 **오히려 빨랐다.**
프리필도 2,050토큰을 1.10초(1,865 tok/s)에 처리했다. 둘 다 병목이 아니다.

### 결정적 단서

보고서에 저장된 **실제 답변이 100~450자(50~200토큰)**였다. 33 tok/s면 1~6초 분량인데
측정 지연은 43~123초. **약 75초가 설명되지 않았다.**

### 진단 — 보이지 않는 thinking 토큰

동일 질문으로 thinking만 바꿔 측정:

| | 생성 토큰 | 소요 |
|---|---:|---:|
| `think=true` | 257토큰 | 35.1초 |
| `think=false` | 50토큰 | 6.0초 |

원인은 `ChatClientFactory`가 `defaultOptions`를 통째로 지정하면서 **`application.yaml`의
`ollama.chat.options.think: false`가 요청에 실리지 않은 것**이었다. 설정 항목은 존재했지만
전달 경로가 끊겨 있었다.

### 검증 — 끄는 것이 답은 아니었다

| 지표 | thinking ON | thinking OFF |
|---|---:|---:|
| 평균 지연 | 88.9s | **33.0s** (−63%) |
| p95 지연 | 188.6s | **74.5s** (−60%) |
| 출처 표시율 | 100% | 100% |
| 필수 사실 포함률 | 77.8% | **57.1%** (−20.7%p) |

thinking은 실제로 근거 활용도에 기여하고 있었다. **속도 2.7배와 품질 20.7%p를 정면으로
맞바꾸는 관계**이므로 기본값은 품질 우선(ON), `BTLLM_THINKING=false`로 선택 가능하게 했다.

### 교훈

이 문제는 `keep-alive: -1` 회귀와 **같은 계열**이다. 그때는 값의 *형식*이 틀려서,
이번은 *전달 경로*가 끊겨서 설정이 무시됐다. 두 경우 모두 앱은 정상 기동했고 설정 파일에는
올바른 값이 적혀 있었다. **설정이 존재한다는 것과 그 값이 실제 요청에 실린다는 것은 다른
문제다.** 프레임워크가 기본값을 덮어쓰는 지점(`defaultOptions`)은 특히 위험하다.

### 다음

지연과 품질이 맞바꿔지므로 **질의 성격에 따라 thinking을 자동 선택하는 라우팅**이 자연스러운
다음 단계다. 단순 조회·문서 요약은 OFF, 트랙 비교·복합 추론은 ON.

## 2026-08-27 — 의도 기반 thinking 라우팅: 작동하지만 측정되지 않음

### 설계

thinking이 지연과 품질을 정면으로 맞바꾸므로(ON 88.9s/77.8% vs OFF 33.0s/57.1%),
복합 추론이 필요한 질의에만 켜는 `ThinkingRouter`를 만들었다.

세 가지 판단:

1. **LLM 분류기를 쓰지 않는다.** 라우팅에 LLM을 한 번 더 호출하면 지연을 줄이려는 목적과
   모순된다. 정규식 판정은 사실상 0ms다.
2. **골든셋에 맞춘 규칙을 만들지 않는다.** 평가셋에 과적합되면 측정이 무의미해진다.
   도메인 무관한 한국어 신호로 한정했다 — 비교·구분(`차이`, `각각`, `~별로`),
   요약·종합(`요약`, `개요`, `핵심`), 이유·판단(`왜`, `근거`).
3. **애매하면 thinking을 켠다.** 문서 정확도가 서비스의 존재 이유이므로, 틀리게 빨리 답하는
   것보다 느리더라도 맞게 답하는 쪽이 기본값이어야 한다.

운영 경로(`ChatWebSocketHandler`)와 실험(`RagGenerationQualityExperiment`) **양쪽에 같은
라우팅을 적용**했다. 실험만 라우팅을 타지 않으면 실제 서비스와 다른 조건을 재게 된다.
보고서에는 문항별 라우팅 판정 사유를 남겨, 어떤 모드로 답한 결과인지 확인할 수 있게 했다.

### 단위 테스트가 잡은 결함

`"사업자등록이 필요한 라운드가 트랙별로 언제인지"`가 `언제` 때문에 단순 조회로 오분류됐다.
`~별로`는 **항목마다 답이 달라진다**는 신호이므로 단순 조회보다 우선하도록 비교 패턴에 추가했다.
규칙 기반 라우팅의 전형적인 함정이고, 테스트가 없었다면 놓쳤을 것이다.

### 결과 — 메커니즘은 작동하나 평가셋이 효과를 드러내지 못한다

| 문항 | 라우팅 판정 | 통과 | 지연 |
|---|---|---|---:|
| application-1 | **단순 조회 → OFF** | ✅ 4/4 | **23.7s** |
| 나머지 7문항 | 비교·요약·기본값 → ON | 4/7 | 89.2~145.7s |

단순 조회로 분류된 문항이 **23.7초에 품질 손실 없이 통과**했다. 나머지 대비 4~6배 빠르다.
라우팅 메커니즘 자체는 의도대로 동작한다.

그러나 총합 지표에는 드러나지 않는다.

| | thinking ON 전부 | 라우팅 |
|---|---:|---:|
| 문항 통과율 | 50.0% | 50.0% |
| 필수 사실 포함률 | 77.8% | 71.4% |
| 평균 지연 | 88.9s | 105.4s |

### 원인 — 측정 설계의 실수

**골든셋 8문항 중 7개가 복합 질의였다.** 이 평가셋은 "문서에서 사실을 정확히 뽑아내는가"를
재려고 만든 것이라 개요·비교·트랙별 구분 질문으로 채워져 있다. 라우팅이 갈릴 여지가
거의 없으니 사실상 "전부 ON"과 같은 실행이었고, 평균 지연이 오히려 높은 것은 GPU 상태 차이로
보인다(같은 ON 조건인데 문항별 89~146초로 흔들림).

**측정을 시작하기 전에 평가셋의 질의 분포를 확인했어야 한다.** 개선안을 만들기는 쉽지만,
그 개선이 드러날 수 있는 측정 조건인지 먼저 따지는 것이 순서다.

### 현재 판단

- 라우팅은 유지한다. 단일 문항 증거(23.7초, 품질 손실 없음)가 메커니즘 작동을 보여주고,
  실사용 질의는 골든셋보다 단순 조회 비중이 높을 것으로 예상되기 때문이다.
- 다만 **"라우팅으로 지연이 개선됐다"고 주장하지 않는다.** 현재 평가셋으로는 입증되지 않았다.
- 효과를 실제로 재려면 단순 조회와 복합 추론이 섞인 별도 평가셋이 필요하다. 이때 기존
  골든셋을 고쳐 쓰면 안 된다 — 그것은 개선을 좋아 보이게 하려고 평가 기준을 바꾸는 것이 된다.

## 2026-08-27 — 고착된 실패 3문항의 근본 원인: PDF 표 구조 소실

### 배경

`track-1`·`registration-1`·`prize-1`은 로컬·상용 두 모델이 **12회 시도 전부 실패**했다.
모델 교체로 풀리지 않음이 확정됐으므로 남은 원인은 파이프라인이다. 셋 다 **두 트랙의 정보를
모두 모아야** 답할 수 있고, 금지 패턴은 트랙 간 **교차 귀속**을 잡는다.

### 진단 1 — 검색이 근거를 주고 있는가

`TrackAttributionDiagnostic`을 만들어 최종 답변이 아니라 **검색 근거**에 필수 사실이
존재하는지만 확인했다. topK를 3/4/5/8로 바꿔가며 측정했다.

| 문항 | topK=3 | topK=4 | topK=5 | topK=8 |
|---|---:|---:|---:|---:|
| track-1 | 1/2 | 1/2 | 1/2 | 1/2 |
| registration-1 | 1/3 | 1/3 | 1/3 | 1/3 |
| prize-1 | **0/2** | 0/2 | 0/2 | 0/2 |

**topK를 8까지 올려도 필수 사실이 근거에 들어오지 않는다.** 후보 폭을 넓히는 것은 해결책이
아니다(오히려 근거가 num_ctx 4096을 다시 초과한다). 검색 문제로 확정.

### 진단 2 — 문서에 정보가 있기는 한가

벡터 스토어를 직접 조회했다. 상금 정보는 **존재한다.**

```
… 상금 MVP제작 육성프로그램 지원 육성프로그램 1:1멘토링 5억원 1:1멘토링 1억원 …
```

같은 청크 안의 위치를 재봤다.

| 토큰 | 위치 |
|---|---:|
| `5억원` | 1,290 |
| `일반/기술` | 2,076 (**786자 떨어짐**) |
| `로컬` | 2,286 |

### 근본 원인

원문 PDF에서 두 트랙의 지원 내용은 **나란히 놓인 두 개의 표**였다. `PagePdfDocumentReader`가
이를 텍스트로 평탄화하면서 **열 구조가 사라졌고, 트랙 레이블과 값의 연결이 끊어졌다.**
`1:1멘토링 5억원 1:1멘토링 1억원`처럼 두 트랙 값이 레이블 없이 나란히 붙는다.

즉 **"일반/기술트랙 = 5억"이라는 정보가 색인된 데이터에 애초에 존재하지 않는다.**
모델은 값의 등장 순서로 추측할 수밖에 없고, 그래서 교차 귀속이 발생한다.

이것으로 **왜 상용 모델도 12회 전부 실패했는지가 완전히 설명된다.** 근거에 없는 사실은
어떤 모델도 만들어낼 수 없다. 만약 맞혔다면 그것이야말로 환각이었을 것이다.

### 결론 — 문제의 층위가 바뀌었다

이 실패는 검색 문제도 생성 문제도 아니라 **ETL(문서 파싱) 문제**다. 지금까지의 개선
(재정렬, 청크 크기, thinking)은 모두 파싱된 텍스트를 전제로 한 것이었고, 그 전제 자체가
이 문항들에서는 무너져 있었다.

**교훈**: RAG 품질을 검색과 생성 두 층으로만 나눠 보면 그 아래 층(파싱)을 놓친다.
"근거가 있는데 못 쓴다"와 "근거가 없다" 사이에는 **"근거는 있는데 의미 연결이 파괴된 채로
있다"**는 상태가 존재한다. 원문을 직접 열어보기 전까지는 이 상태를 볼 수 없다.
