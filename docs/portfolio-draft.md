## 01 — ABOUT

상용 LLM API는 품질이 좋지만 문서 본문이 외부로 전송되고 사용량만큼 과금된다. 정부
공고문·계약서·사내 매뉴얼처럼 **밖으로 나가면 안 되는 문서**를 다루려면 로컬에서 끝나는
파이프라인이 필요하다고 판단했다. "로컬 모델은 느리고 부정확하다"는 전제를 **직접 재고 확인**하는
것이 이 프로젝트의 출발점이었다 — 매 개선을 골든셋 기반 자동 평가로 검증하고, 가설이 틀리면
틀렸다고 기록했다.

## 03 — ARCHITECTURE

```
[React + TypeScript]
        │  WebSocket(토큰 스트리밍)  /  REST(인증·문서·이력)
        ▼
[Spring Boot 3.5 + Spring AI 1.1]
        │
        ├─ ChatClientFactory ── Advisor 체인(가드→대화이력→토큰추적→로깅)
        │                       provider 라우팅: ollama / openai / claude / gemini
        │
        ├─ LlmTools (Tool Calling)
        │     └─ searchKnowledgeBase → pgVector 검색 → HybridReranker 재정렬
        │
        ├─ OllamaGenerationQueue ── GPU 물리 1슬롯 admission control
        │
        └─ EtlPipelineService(@Async)
              Reader → TokenTextSplitter → SafeUrlFetcher(SSRF 가드) → 임베딩 → pgVector
        │
        ▼
[Ollama: qwen3:8b(생성) + bge-m3(임베딩)]   [PostgreSQL + pgvector]
```

**실행 제약 — 모든 수치의 전제**: RTX 4060 Ti **8GB**. qwen3:8b(5.6GB) + bge-m3(0.7GB)로
여유는 약 1.7GB뿐이다. 이 한 줄이 청크 크기·재정렬 방식·GPU admission control까지 대부분의
설계를 규정한다.

## 04 — KEY CONTRIBUTION

### #001 — LLM 응답을 재현 가능하게 측정하는 평가 하네스

LLM 애플리케이션은 "고쳤더니 좋아진 것 같다"가 통하지 않는다. 같은 질문도 매번 다른 답이
나오고, 프롬프트 한 줄이 무관한 시나리오를 조용히 깬다. **개선보다 먼저 측정 체계를 만들었다.**

| 하네스 | 대상 | 판정 방식 |
|---|---|---|
| `ragAccuracyExperiment` | 청크 크기별 검색 Recall | 골든셋 35건 |
| `ragGenerationQualityExperiment` | 최종 답변 품질 | 필수 사실·금지 오답·출처 정규식 |
| `providerComparisonExperiment` | 동일 조건 모델 비교 | 위 판정기 재사용, 3회 반복 |
| `localConversationQualityExperiment` | 정체성·기억·출력 계약 | 시나리오 4종 |

**설계 원칙**
- 판정기를 실험과 분리해 단위 테스트로 검증한다 — 평가 기준 자체가 틀리면 모든 수치가 무의미하다.
- 실 Ollama·상용 API 호출 실험은 태그로 CI에서 격리한다 — provider 비교는 실제 과금이 발생한다.
- **단발 결과를 믿지 않는다.** provider 비교 1차 실행은 "로컬 62.5% vs 상용 62.5% 동률"이었다 —
  원하던 결론이라 더 위험했다. 3회 반복하자 로컬 50.0%/상용 58.3%로 정정됐고, 오히려
  **편차는 상용 쪽이 더 컸다**(12.5%p vs 로컬 0.0%p) — 처음 가정과 반대였다.

### #002 — 컨텍스트 예산에 맞춘 RAG 파이프라인 재설계

**문제**: 청크 크기 1500토큰이 한국어 공고문에서 평균 5,425자 청크를 만들었다. `topK=3` 근거만
약 4,521토큰 — 설정된 `num_ctx` 4,096을 **검색 단계에서 이미 초과**하고 있었다. 검색이 정답을
찾아줘도 모델은 그 뒷부분을 보지 못했다.

**조치**: 청크 크기를 800토큰으로 낮추고 설정값(`btllm.rag.chunk-size`)으로 분리했다. 색인 시점
파라미터라 재색인이 필요하고, 골든셋으로 크기별 효과를 비교하려면 코드 수정 없이 주입할 수
있어야 하기 때문이다.

```
청크 1500 (38청크)           청크 800 (63청크)
문항 통과율     0.0%     →         50.0%
사실 포함률    38.1%     →         76.2%
평균 응답시간   65.8s     →         50.6s   (지연도 함께 -23%)
```

**의미**: 이 수치는 gpt-4o-mini의 사실 포함률(76.2%)과 동일하다. 직전까지 "모델 체급 문제"로
분류했던 실패 상당수가 실제로는 컨텍스트 초과였다는 뜻이다 — provider 비교만으로는 두 모델이
*동일하게 잘린 근거*를 받고 있다는 공통 결함을 볼 수 없었다.

## 05 — TROUBLESHOOTING

### #001 — 설정값 하나가 채팅 전체를 마비시킨 회귀

`Ollama keep-alive 설정` → `채팅 요청 100% 실패` → `Spring AI 옵션 직렬화`

| 증상 | 원인 | 해결 |
|---|---|---|
| k6 baseline 에러율 **100%** | YAML 정수 `-1`이 String 필드로 직렬화돼 `"-1"`로 전송 | 단위 명시 `-1s` |

**증상**: 콜드스타트 제거를 위해 `keep-alive`를 적용한 직후 k6 baseline 에러율이 100%로 튀었다.

**원인**: 로컬 프록시로 백엔드→Ollama 요청을 가로채 원문을 확보하니 응답이
`{"error":"time: missing unit in duration \"-1\""}`. YAML에 정수 `-1`을 썼지만 Spring AI의
`keepAlive` 필드가 String이라 `"-1"`로 직렬화됐고, Ollama의 Go `time.ParseDuration`이 단위
없는 값을 400으로 거부하고 있었다.

**해결 & 검증**: `-1s`로 단위 명시. 에러율 **100% → 0%**, 콜드스타트 **37,197ms → 1,246ms
(약 30배)**.

> **교훈**: Spring Boot의 relaxed binding이 숫자를 조용히 문자열로 바꾼다. 기동 성공과 동작
> 정상은 다른 문제다 — 설정값의 *형식*까지 실제 요청 로그로 검증해야 한다.

### #002 — Advisor를 Tool로 바꾼 뒤 RAG가 완전히 죽어 있던 문제

`상시 Advisor → Tool Calling 전환` → `문서 검색 호출률 0%` → `Tool description 문구`

**증상**: PDF 색인 후 "방금 준 문서 무슨 문서야?" → "어떤 문서도 제공받지 않았어요."

**원인**: `vector_store` 직접 조회로 청크가 정상 적재된 것을 확인해 ETL 문제를 배제했다. 도구
호출 로그가 0건이었고, Ollama API를 직접 격리 테스트하니 억제형 description(`"…필요할 때만
사용하세요"`)에서는 `tool_calls: null`, 단정형으로 바꾸면 정상 호출됐다. **원인은 description의
어조**였다.

**해결 & 검증**: description을 단정형으로 교체, 도구 호출 로그 추가. 호출률 **0% → 100%**.
추가로 "무슨 문서야?" 같은 메타 질문은 문서 *내용*과 의미적으로 안 가까워 검색이 구조적으로
0건을 내는 것도 발견해, 0건일 때 인덱싱된 문서 목록을 대신 반환하도록 보완했다.

> **교훈**: 상시 Advisor를 Tool로 바꾸는 것은 최적화가 아니라 **"동작 여부의 결정권을 모델에게
> 넘기는" 설계 변경**이다. 작은 로컬 모델은 description 어조 하나로 호출률이 0%와 100%를 오간다.

### #003 — 짧은 답변에 100초가 걸리던 문제: 설정은 있는데 전달되지 않았다

`3회 반복 지연 측정` → `p95 188.6초` → `defaultOptions가 think 설정을 덮어씀`

**증상**: 평균 지연 88.9초, p95 **188.6초**. DB 저장된 실제 답변은 100~450자뿐이라, 33 tok/s면
1~6초면 끝날 분량인데 **약 75초가 설명되지 않았다.**

**진단 과정 — 두 번 틀렸다**
1. "출력이 길다"는 가설로 `num_predict`를 512로 제한 → 지연은 8.4초만 줄고 **출처 표시율이
   100%→37.5%로 붕괴**(`[출처]`는 답변 끝줄이라 절단되면 먼저 깨짐). 되돌림.
2. VRAM 압박을 의심했으나 VRAM 93%에서도 생성 속도는 오히려 더 빨랐다(36.1 tok/s).
3. 동일 질문을 thinking 모드만 바꿔 재현: `think=true` 257토큰/35.1초, `think=false`
   50토큰/6.0초. **보이지 않는 `<think>` 토큰이 시간을 다 쓰고 있었다.**

**원인**: `application.yaml`의 `ollama.chat.options.think: false`가 설정돼 있었지만,
`ChatClientFactory`가 `defaultOptions`를 통째로 지정하면서 이 값이 실제 요청에 실리지 않고
있었다. 설정 항목은 존재했지만 전달 경로가 끊겨 있었다.

**해결 & 검증**: thinking을 명시적으로 제어하도록 수정.

```
평균 지연        88.9s → 33.0s   (-63%)
p95 지연        188.6s → 74.5s   (-60%)
사실 포함률       77.8% → 57.1%   (-20.7%p, 트레이드오프)
```

thinking을 끄는 것이 정답은 아니었다 — 근거 활용도에 실제로 기여하고 있었다. 그래서 기본값은
품질 우선(ON)으로 두고, 복합 추론이 필요한 질의만 판별하는 `ThinkingRouter`를 추가로 만들었다.
단순 조회로 분류된 문항은 **23.7초에 품질 손실 없이** 통과했다.

> **교훈**: #001과 같은 계열이다 — 그때는 값의 *형식*이, 이번은 *전달 경로*가 끊겨서 설정이
> 무시됐다. 둘 다 앱은 정상 기동했고 설정 파일에는 올바른 값이 있었다. 설정이 존재하는 것과
> 그 값이 실제 요청에 실리는 것은 다른 문제다.

### #004 — GPU가 1개인데 요청은 무한정 쌓일 수 있었다

`WebSocket 메시지마다 독립 subscribe` → `Disposable 반환값 방치` → `admission control 부재`

**증상**: 부하테스트에서 동시 2~3명이면 대부분 30초를 넘겼다. 원인은 GPU가 느려서만이 아니었다
— 세션마다 여러 요청을 동시에 시작할 수 있었고, 연결이 끊겨도 이미 시작된 Ollama 호출이
백그라운드에서 GPU를 계속 점유했다. `QUEUED` 응답은 안내 문구일 뿐 서버가 순서를 강제하지
않았다.

**원인**: `.subscribe(onNext, onError, onComplete)`의 반환값(`Disposable`)을 버리고 있었다 —
취소할 방법 자체가 없었다.

**해결**: GPU 1슬롯에 맞춰 `ThreadPoolExecutor(core=max=1, bounded queue)`로 동시성을 강제했다.
여기서 지나갈 뻔한 함정: Reactor의 `.subscribe()`는 비동기라서 큐 워커 스레드에 그대로 넘기면
스레드가 즉시 반환되고 큐가 아무것도 직렬화하지 못한다.

```java
// 워커 스레드를 실제로 점유해야 동시성 제약이 의미를 갖는다
finalPrompt.stream().chatResponse()
    .doOnNext(response -> forwardToken(session, provider, response))  // 토큰은 도착 즉시 전송
    .blockLast();                                                      // 스레드는 여기서 실제로 블로킹
```

세션당 취소 핸들(`Future`/`Disposable`)과 세대 카운터를 둬, 새 요청이 이전 요청을 취소하고
연결 종료 시에도 진행 중 작업을 정리하게 했다. 상용 provider는 이 큐를 거치지 않는다 — 로컬
GPU를 물리적으로 공유하지 않기 때문이다.

> **교훈**: "동시성=1"이라는 제약은 스레드가 실제로 점유돼 있어야 의미를 갖는다. 비동기
> 콜백에 작업을 넘기는 순간 그 보장은 조용히 사라진다.

## 06 — SECURITY

로컬 개인 PC용 앱이라는 인상과 달리, 공개 회원가입과 JWT 인증이 있는 **다중 사용자 웹
서비스**였다. 별도 정적 스캔(Critical 1 · High 5 · Medium 2) 이후 기능 개발을 멈추고 외부
노출 전 필수 항목을 순서대로 고쳤다.

| # | 취약점 | 조치 |
|---|---|---|
| 1 | Compose가 저장소에 공개된 고정 JWT 키로 기동 — 알면 임의 사용자로 토큰 위조 가능 | 미설정·저엔트로피 키는 **기동 자체를 실패**시킴(안전 실패). JWT subject를 매 요청 DB와 대조 |
| 2 | RAG 지식베이스에 소유권 경계 없음 — 로그인한 누구나 타인 문서 열람·삭제 가능 | 사용자별 소유 모델 도입, `owner_id` predicate를 목록·삭제·검색 전 경로에 강제. 검색은 신원 없으면 **거부**(fail-closed) |
| 3 | ETL·LLM 크롤러가 SSRF에 열려 있음 — 내부망·클라우드 메타데이터 엔드포인트 접근 가능 | scheme/포트 allowlist + **DNS 해석 결과** 기반 사설 IP 차단, 리다이렉트 매 홉 재검증 |
| 4 | Docker 인프라 기본 포트·기본 계정 노출 | DB·모니터링 포트 loopback 바인딩, 기본 계정 제거·안전 실패 전환 |

**정직하게 남긴 한계**: SSRF 가드는 검증-연결 사이 DNS가 바뀌는 rebinding까지는 막지 못한다 —
완전 차단하려면 주소 pinning이 필요하고, 현재 위협 모델(로컬 단일 사용자)상 우선순위를
낮췄다는 판단을 코드에 남겼다. "안 한 이유"를 남기는 것도 "한 것"만큼 중요하다고 봤다.
